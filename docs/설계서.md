## 0. 설계의 대전제

1. **돈은 엔진이 계산하고, 포털은 보여준다.** 포털은 어떤 수수료·환수·세액도 스스로 산출하지 않는다. 허용되는 연산은 엔진이 확정한 정수(원) 금액의 **합산과 비율 표시**뿐이다. 세후 실수령액·시뮬레이션 결과는 반드시 엔진에서 받아온다.
2. **상태를 섞지 않는다.** 설계사 신뢰의 핵심은 숫자 자체가 아니라 그 숫자가 **예상(잠정)인지, 확정(마감)인지, 지급완료인지**를 화면이 절대 흐리지 않는 것이다. 모든 금액 옆에는 상태가 붙는다.
3. **읽기 모델은 언제든 처음부터 다시 만들 수 있어야 한다.** 포털 DB는 엔진 이벤트 스트림의 파생물이다. 이벤트 seq 0부터 replay하면 동일한 화면이 재현된다(결정론). 이것이 장애·정정·의심 상황의 유일한 복구 수단이다.
4. **테넌트 격리는 구조로 강제한다.** 본 솔루션은 여러 GA(보험사 자회사형 GA 등)에 공급된다. `tenant_id` 조건이 없는 데이터 접근은 테스트·기동 단계에서 실패해야 하며, DB 수준(RLS)에서 한 번 더 막는다.
5. **설계사 화면에는 설계사 자신의 것만, 필요한 만큼만.** 타인의 수수료·사규 요율표·고객 식별정보는 화면에 나오지 않는다. 시뮬레이션은 설계사 내부 참고용이며 고객 제시 자료가 아니다(§2.3).

## 1. 문제 정의와 사용자

### 1.1 왜 지금 이 화면이 필요한가

| 환경 변화 | 설계사에게 생긴 질문 | 현재 답을 얻는 방법 |
|---|---|---|
| 2026-07-01 1200%룰이 GA→설계사 개인별 지급에 확대 적용(시책·정착지원금 합산) | "이 계약으로 앞으로 시책을 더 받을 수 있나, 한도가 얼마 남았나" | 정산팀에 문의, 또는 모름 |
| 2027-01 분급제 시행 예정(초년도 수수료를 수년에 걸쳐 분할 지급, 감독규정 확정 고시 확인 필요) | "내년부터 매달 실제로 얼마가 들어오나" | 엑셀로 스스로 추정 |
| 환수(해약·실효·철회)의 상계 | "이 계약이 해약되면 이번 달 지급에서 얼마가 빠지나" | 지급명세 받고 나서야 앎 |
| 대형 GA 13개월 정착률 57.8%(2024년 말 기준, 보도), 설계사 이동 증가 | "지금 GA에 남는 게 나은가" — 수입 예측 불가가 이탈을 부추김 | 없음 |

정산 시스템(엔진)은 이 정보를 **전부 이미 가지고 있다**(한도 원장, 분급 스케줄, 환수 채권, 마감 명세). 문제는 설계사가 볼 수 없다는 것뿐이다. 따라서 본 시스템의 본질은 "새 계산"이 아니라 **엔진 원장의 설계사 관점 투영(projection)** 이다.

### 1.2 사용자와 권한 범위

| 사용자 | v1 범위 | 볼 수 있는 것 |
|---|---|---|
| 설계사(본인) | **핵심** | 본인 수수료·한도·분급·환수·명세·알림·시뮬레이션 |
| 조직장(팀장/지점장/본부장) | v2 | 본인 것 + 하위 조직 합계 + 본인 오버라이드 라인. 개별 팀원 라인은 사규 파라미터 |
| 정산 담당자 | v2(지원 콘솔) | 이의제기 응대, 대사 결과, 인제스트 상태, 재구축 실행 |
| 시스템 운영자 | v1(CLI/관리 API) | 테넌트 등록, 인제스트 커서, 재구축 |

### 1.3 설계사의 다섯 가지 질문 (Jobs-to-be-done) → 화면

| # | 질문 | 화면 | 데이터 출처 |
|---|---|---|---|
| Q1 | 이번 달 얼마 들어오나 (세전/세후, 언제) | 홈 | `earnings_month` + 엔진 명세 스냅샷 |
| Q2 | 이 계약 한도가 얼마 남았나, 왜 깎였나 | 한도 현황 | `policy_limit` + 이력 |
| Q3 | 앞으로 매달 얼마 나오나 | 분급 타임라인 | `deferral_item` |
| Q4 | 이 계약이 해약되면 얼마 물어내나 | 시뮬레이션(해약 영향) | 엔진 동기 API |
| Q5 | 이 계약을 체결하면 얼마 받나 | 시뮬레이션(신계약) | 엔진 동기 API |

### 1.4 비즈니스 모델이 설계에 미치는 영향

본 솔루션은 자체 구축 GA 운영 IT 솔루션의 일부로 **보험사 자회사형 GA 등 여러 GA에 공급**된다. 따라서:

- 포털은 **멀티테넌트**다. 한 배포로 여러 GA를 서비스하되 데이터는 완전 격리한다.
- 수수료 엔진은 **교체 가능한 공급원**이어야 한다. 우리 엔진이 기준 구현이지만, 자체 정산 시스템을 보유한 GA는 어댑터로 같은 이벤트 계약(§4)을 맞추면 포털을 그대로 쓸 수 있다. 이것이 포털과 엔진을 **계약(Contract)으로만** 결합하는 이유다.
- 도입 GA의 기존 설계사 앱 안에 **웹뷰로 임베드**될 가능성이 높으므로 모바일 우선 웹으로 만든다.

- 설계사가 보는 요율 정보는 **자기 계산 라인의 근거(적용 요율·지급률·회차)의 실제 수치** 로 한정한다(확정, §14.0). 사규 요율표 전체, 타인 등급·지급률, 다른 상품의 요율은 노출하지 않는다 — 라인 근거는 "이 라인이 왜 이 금액인가"에 답하는 범위까지다.

## 3. 시스템 아키텍처

### 3.1 아키텍처 결정 (Decision Record)

|---|---|---|---|
| D-1 | **별도 저장소·별도 배포** (`ga-agent-portal`). 엔진과는 §4 계약으로만 결합 | 사용자(설계사 vs 정산팀), 노출면(외부 모바일 vs 내부), 배포 주기, 보안 등급이 전부 다르다. 엔진 저장소 내부의 "정본 문서=코드 동일 커밋" 원칙은 각 저장소 안에서 그대로 유지 | 엔진 `commission-api`에 설계사 화면 추가 — 외부 노출면이 돈 원장과 같은 프로세스에 생김 |
| D-2 | **엔진은 테넌트별 인스턴스(물리 분리), 포털은 멀티테넌트(논리 분리 + RLS)** | 돈 원장은 GA별로 분리 배포하는 것이 고객(GA)의 감사·격리 요구에 부합하고 엔진 코드 변경이 없다. 포털은 읽기 전용이라 논리 분리로 충분하며 운영 단가가 낮다 | 엔진 멀티테넌트화 — 원장·락·마감 전부에 tenant 축이 추가되는 대수술 |
| D-3 | **CQRS 읽기 모델 + 아웃박스 pull 피드** (브로커 없음) | 설계사 조회 패턴(설계사×월 키 조회, 마감 익일 오전 집중)은 엔진의 계산 원장 스키마와 맞지 않는다. 엔진 장애와 무관하게 조회가 가능해야 한다. 브로커 없이 커서 기반 pull이면 포트폴리오 실행이 단순하고, Kafka 등으로의 교체는 인제스트 어댑터 한 개 교체로 끝난다 | 화면마다 엔진 동기 조회 — 엔진 가용성에 종속, 집중 시간대 부하 전가 |
| D-4 | **세후 잠정치·시뮬레이션은 엔진의 dry-run API로** | 원천세·상계 순서·환수율은 엔진 룰이다. 포털이 흉내 내는 순간 두 숫자가 어긋난다(대전제 1) | 포털에서 3.3% 곱하기 — 세율·상계 규약이 파라미터라 언젠가 틀린다 |
| D-5 | **포털 DB는 PostgreSQL** (엔진은 Oracle 유지) | 행 수준 보안(RLS)으로 테넌트 격리를 DB가 2차 방어, JSONB로 라인 근거 저장. 읽기 모델은 엔진 DB와 무관하므로 선택 자유 | Oracle 통일 — 고객사 표준이 Oracle이면 어댑터 교체로 대응 가능(도메인·프로젝터는 DB 무의존) |
| D-6 | **모바일 우선 웹(PWA)**, 네이티브 앱 없음 | 도입 GA의 기존 앱에 웹뷰 임베드가 현실적 배포 경로. 한 코드베이스 | 네이티브 — 포트폴리오 범위 초과 |

### 3.3 모듈 구성 (Gradle 멀티모듈 + pnpm)

```
ga-agent-portal/
├── contracts/                # 엔진↔포털 계약: JSON Schema (events/v1/*.json, api/v1/openapi.yaml) + shared/ga-disclosure/(공유 Envelope 핵심 사본, v1.2)
├── portal-domain             # 포털 고유 값객체(CalcId, PolicyNo, LedgerId, ScheduleId, CommType), 뷰 모델, 상태 열거형. platform-core만 의존
├── portal-projection         # 프로젝터(이벤트→뷰 변환) 순수 로직 + 알림 파생 규칙. DB 무의존
├── portal-ingest             # 이벤트 피드 클라이언트, 커서, 멱등 적용, 실패 격리, 재구축 실행기
├── portal-query              # 조회 서비스·REST 컨트롤러, 인가 정책
├── portal-sim                # 엔진 시뮬레이션·명세 dry-run 프록시, simulation_log
├── portal-recon              # 대사 배치, DRIFT 상태 전이, 관측 지표
├── portal-infra              # PostgreSQL 어댑터(platform-spring `TenantScopedRepository` 하위 저장소), RLS 세션 바인딩, Flyway
├── portal-app                # Spring Boot 조립, 보안 설정, 스케줄러
├── portal-demo               # 데모 테넌트 데이터 생성기(§부록 B), 로컬 엔진 대체용 이벤트 재생기
└── web/                      # React 19 + TypeScript + Vite, pnpm — 빌드 산출물은 portal-app 부트 jar 안(같은 출처, v1.7). PWA(서비스 워커)는 v2
```

의존 방향: `app → query/ingest/sim/recon → projection → domain`. `infra`는 어댑터로서 `app`에서만 조립된다. `projection`은 DB·Spring 무의존이어야 하며(인메모리 저장소로 밀리초 단위 테스트), 이는 엔진의 `commission-calc` 원칙과 동일하다.

**플랫폼 아티팩트(v1.2)**: 공용 값객체 `Won`·`Ratio`·`Ym`·`TenantId`·`AgentId`와 `TenantContext`는 ga-disclosure가 발행하는 `com.ga.platform:platform-core` 0.2.0의 것을 쓴다(§11 플랫폼 행). 포털은 같은 단순 이름의 클래스를 만들지 않고(아키텍처 테스트), 플랫폼 API가 모자라면 포털에서 보충하지 않고 ga-disclosure 쪽 정비로 올린다. `portal-domain`·`portal-projection`이 의존할 수 있는 외부 모듈은 `platform-core`뿐이고, `platform-spring`(세션 바인딩·저장소 기반 클래스)은 `infra`·`app`에서만 쓴다.

### 3.4 데이터 흐름 3종

1. **투영 경로(비동기)**: 엔진 트랜잭션 커밋 → OUTBOX 적재 → 포털 poller(테넌트별, 주기 5~30초) → `ingest_event` 멱등 검사 → 프로젝터 적용 + 알림 파생(같은 트랜잭션) → 커서 전진. 화면은 `asOf(seq, at)`를 항상 함께 표시한다.
2. **동기 경로**: 시뮬레이션·잠정 명세 갱신 요청 → `portal-sim` → 엔진 API(서비스 토큰) → 결과 로그 → 응답. 엔진 불가 시 화면은 "잠시 후 다시" + 마지막 스냅샷 시각을 보여주고 **투영 경로 데이터는 그대로 서비스**한다.
3. **대사 경로(배치)**: 매일 새벽 테넌트별로 당월(ESTIMATE)·직전 마감월(CONFIRMED) 명세를 엔진에서 받아 포털 합산과 비교 → 불일치 시 해당 설계사×월을 `DRIFT`로 표시하고 화면에 "확인 중" 배지 → 자동 재구축 시도 → 지속 시 운영 알림.

## 4. 엔진↔포털 통합 계약 (Integration Contract v1)

계약은 `contracts/` 폴더에 JSON Schema·OpenAPI로 둔다. 엔진 저장소는 같은 스키마로 **발행 이벤트를 검증하는 provider 테스트**를 가진다(§13). 스키마 변경은 `version` 필드 증가와 호환성 규칙(§4.5)을 따른다.

**계약 규약(v1.2)**:
- `contracts/`는 두 부분이다. `contracts/shared/ga-disclosure/`는 ga-disclosure가 소유한 **공유 Envelope 핵심**(`events/v1/envelope-core.schema.json`)의 사본이고 고치지 않는다 — 바꿔야 하면 ga-disclosure에서 작은 PR → 병합 → `UPSTREAM`을 그 병합 커밋으로 옮기고 다시 받는다. 그 밖(`events/v1`·`api/v1`)은 포털 정본이다.
- 사본 디렉터리에는 전용 `CHECKSUMS`(파일 바이트의 평문 SHA-256, `sha256sum -c` 형식)와 `UPSTREAM`(첫 줄 `hjryoo-ai/ga-disclosure@<40자 병합 커밋>`, 다음 줄부터 파일 목록)을 둔다. `verifyContractChecksums`(오프라인, `check`)는 포털 정본의 `contracts/CHECKSUMS`와 사본의 `CHECKSUMS`를, `verifyUpstreamContract`(네트워크, CI)는 **사본만** 업스트림과 바이트 대조한다 — `contracts/` 전체를 대조하면 포털 정본이 업스트림에 없어 실패한다. JCS(`platform-canonical`)는 이벤트 payload의 정규 해시(멱등·중복 판정)에만 쓴다.
- 금액은 `integer`(정수 원). 날짜·시각·UUID는 `format`이 아니라 `pattern`이다(소비 측 검증기가 `format`을 단언하지 않는다) — `contracts/` 전 파일에 `format` 키워드 0(시험). 요율·지급률·배수 같은 **돈이 아닌 소수는 JSON number가 아니라 불투명 소수 문자열** `^(0|[1-9][0-9]*)(\.[0-9]{1,6})?$`이다(표시 전용 — 소비자는 산술에 쓰지 않는다; JSON number는 파싱하는 순간 `double`·`BigDecimal`이 생긴다): `basis.rate`·`basis.payoutRate`·`LimitLedgerOpened.limitMultiple`.
- **계약 v1.1**(v1.3): 엔진에 그 데이터가 없는 필드는 필수로 두지 않는다 — 엔진이 값을 지어내게 하지 않는다. `policySummary.productName`·`insuredMasked`(엔진에 계약 마스터·고객 데이터 없음), `basis.rate`·`payoutRate`·`installmentNo`(정액·일시 지급은 없음 — `ruleVersionIds`만 필수), `AgentSnapshot.grade`·`role`(등급 이력 없는 설계사, 엔진에 역할 없음), `StatementConfirmed.clawbackOffset`·`withholdingTax`·`net`(지급 런에서 확정)이 선택이다. 선택 필드가 없을 때의 표시는 §8, 역할의 출처는 §9.

### 4.1 이벤트 피드

**엔진 측**(v1.4 — 정본은 엔진 설계서 §6.8 "아웃박스·이벤트 피드", 엔진 E1)

- 엔진은 업무 트랜잭션 안에서 `OUTBOX_EVENT`에 `seq` 없이 행을 넣고, **순번 부여기**가 커밋된 행에만 `seq`를 빈틈 없이 붙인다(Oracle 시퀀스가 아니다 — 시퀀스는 롤백·캐시로 갭이 나고, 낮은 번호가 늦게 커밋되면 poller가 건너뛴다). 피드는 `seq`가 붙은 행만 돌려준다. 그래서 포털이 보는 `seq`에는 **갭이 없고**, 갭은 결함 신호라 포털은 그 테넌트를 멈춘다(§6.1).
- 같은 원장·같은 설계사의 두 사실 사이 순서는 엔진의 잠금(원장 `FOR UPDATE`, 수급자 단위 지급 트랜잭션)이 커밋 순서로 보장한다. 잠금을 공유하지 않는 두 사실의 순서는 보장되지 않으며 포털은 그것에 기대지 않는다.
- append-only(엔진 트리거). 보존 축소(`TenantSnapshot`)는 미결정(§14.1 #4).
- 발행 대상은 설계사(AGENT) 수급자 행뿐 — 조직(ORG) 수급자(오버라이드)는 v1에 나오지 않는다(엔진 E1 D-3).

**피드 API**

```
GET /internal/v1/events?afterSeq={n}&limit={1~1000, 기본 200}
→ { "tenantId": "GA01", "events": [Envelope...], "nextSeq": n', "headSeq": h, "schemaVersion": 1 }
```

- 응답 순서는 `seq` 오름차순, 갭 없음. `headSeq − nextSeq`가 포털의 지연 지표.
- `tenantId`(필수, v1.3)는 응답한 엔진 인스턴스의 테넌트다. 엔진은 테넌트별 인스턴스이므로 잘못된 `engine_base_url`로 다른 테넌트를 읽는 사고를 포털이 응답에서 막는다 — 요청한 테넌트와 다르면 아무것도 적용하지 않고 그 테넌트를 정지한다(§6.1).
- `afterSeq > headSeq` → `422` Problem `{code: AFTER_BEYOND_HEAD, message}`(복원된 DB 등 다른 발행자 — ga-disclosure 피드와 같은 규약). 서비스 토큰이 없거나 틀리면 `401`. 파라미터 오류(afterSeq 없음·음수, limit 범위 밖)는 `400` Problem `{code: INVALID_REQUEST}`(v1.4.1 — 엔진 E1이 이미 낸다).
- 인증: 서비스 토큰(운영은 mTLS 권장). 설계사 토큰으로는 절대 접근 불가.

**Envelope**

```json
{
  "eventId": "6f1c…", "seq": 10231, "type": "CommissionCalculated", "version": 1,
  "occurredAt": "2026-09-22T10:15:30+09:00",
  "aggregate": { "kind": "COMM_CALC", "id": "884213" },
  "payload": { ... }
}
```

포털 Envelope 스키마(`contracts/events/v1/envelope.schema.json`, v1.2)는 `allOf: [공유 핵심, 포털 제약]`이다. 핵심은 일곱 필드(`eventId` UUID·`seq`≥1·`type`·`version`≥1·`occurredAt` 오프셋 포함·`aggregate{kind, id}`·`payload` 객체)와 그 형식이고, 포털 제약은 `type` 13종(§4.2)·`version` 1·`aggregate.kind` 9종과 **`type`(+`version`)별 `if/then`**(payload 스키마, `type` ↔ `kind` 짝)이며 열거 밖의 `type`·`version`은 거부한다(else: false). `oneOf`로 payload를 고르지 않는다 — 모르는 필드를 허용하는 열린 payload와 양립하지 않는다(필드가 겹치는 payload는 둘 다 맞아 실패하고, `type`과 무관한 payload도 통과한다).

| `aggregate.kind` | 이벤트 | `aggregate.id` |
|---|---|---|
| `AGENT` | `AgentSnapshot` | agentId |
| `COMM_CALC` | `CommissionCalculated` | calcId |
| `ADJUSTMENT` | `AdjustmentPosted` | adjId |
| `LIMIT_LEDGER` | `LimitLedgerOpened`·`LimitLedgerPosted`·`LimitLedgerRebased` | ledgerId |
| `DEFERRAL_SCHEDULE` | `DeferralScheduled`·`DeferralStatusChanged` | scheduleId |
| `CLAWBACK_RECEIVABLE` | `ClawbackReceivableUpdated` | receivableId |
| `POLICY` | `PolicyEventObserved` | policyNo |
| `STATEMENT` | `StatementEstimated`·`StatementConfirmed` | `{agentId}:{closeYm}` (정규식으로 강제) |
| `PAYOUT` | `PayoutCompleted` | `{agentId}:{closeYm}` (정규식으로 강제) |

**집계 금액의 정의**(v1.3 — 계약 설명문과 §5 주석이 같은 문장): `gross` = Σ 그 달 `CommissionCalculated` 라인 중 commType ∉ {CLAWBACK, ADJUSTMENT}의 amount — **전 상태 합산**(취소 원본·reversal 모두, 상태로 거르지 않는다), `clawbackOffset` = Σ 그 달 CLAWBACK 라인(≤ 0), `adjustment` = Σ 그 달로 귀속된 `AdjustmentPosted`. `StatementEstimated`·`StatementConfirmed`·`PayoutCompleted`의 세 필드가 이 정의이고 포털 `earnings_month`의 합산과 같아야 §6.6 대사가 성립한다. `PayoutCompleted.receivableOffset`(기존 채권의 자동 상계)은 `clawbackOffset`과 다른 것이다.

환수는 별도 타입이 아니다. 엔진에서 환수는 음수 `COMM_CALC`이므로 `CommissionCalculated(commType=CLAWBACK, amount<0)`로 들어오고, 채권화 여부만 `ClawbackReceivableUpdated`가 보강한다.

### 4.4 엔진 저장소 변경 목록 (ga-commission-engine, 별도 PR)

1. `OUTBOX_EVENT` DDL(Flyway) + `OutboxPublisher implements CalcResultListener` — 저장 후 훅 체인에 등록.
2. 분급 상태 전이(`commission-deferral`), 채권 갱신(`commission-clawback`), 마감·지급(`commission-settlement`), 한도 원장 개설·재산정(`commission-limit`)에 동일 훅 적용.
3. `StatementEstimated` 배치(`commission-batch`): 지급 런 로직을 dry-run 모드로 실행해 설계사별 잠정 명세 발행. 주기는 배치 파라미터(**기본 야간 1회**, 확정 §14.0). 이벤트 후 지연 재산출·온디맨드 갱신은 같은 dry-run 서비스를 다른 트리거로 호출하는 것이므로 주기 변경에 코드 수정이 없어야 한다.
4. `commission-api`: 이벤트 피드(E1), 시뮬레이션 2종·명세 조회 컨트롤러(E2, 기존 로드맵 Phase 9 잔여 흡수).
5. `contracts/events/v1` 스키마에 대한 provider 검증 테스트(골든 시나리오 실행 → 발행 이벤트 시퀀스가 스냅샷과 일치).
6. 마감 이후 해당 `closeYm`의 `CommissionCalculated` 발행 금지 불변식 테스트(이미 마감 불변성 테스트가 있으므로 이벤트 측면만 추가).

### 4.5 계약 버전·호환성 규칙

- 필드 **추가**는 호환(포털은 모르는 필드 무시). 필드 **삭제·의미 변경·타입 변경**은 `version` 증가 + 포털 프로젝터의 버전 분기.
- 포털은 자신이 지원하는 최대 version보다 큰 이벤트를 만나면 **그 테넌트 인제스트를 정지**하고 운영 알림(잘못 해석한 숫자를 보여주는 것보다 멈추는 것이 낫다). 포털 Envelope 스키마가 `version` 1만 받으므로 그런 이벤트는 스키마 검증에서 먼저 걸린다(v1.2).
- Envelope **핵심 필드 집합**은 ga-disclosure와 공유하는 계약이다 — 포털이 바꾸지 않는다(v1.2, 위 계약 규약).
- `seq` 갭·역순·중복은 각각 정지·무시·무시(§6.1).

## 5. 읽기 모델 (포털 스키마, PostgreSQL)

모든 테이블은 `tenant_id`를 첫 컬럼으로 갖고 PK·UNIQUE·인덱스에 포함한다. 금액은 `BIGINT`(정수 원). 이하 핵심 테이블만 기술하며 DDL은 Flyway로 관리한다(정본 `portal-infra/src/main/resources/db/migration/V1__init.sql`).

**제약(v1.2)** — 컬럼은 더하지 않고 V1에 제약만 더했다. ① 형식 `CHECK`(정규식): `tenant_id` = 플랫폼 `TenantId`(`^[A-Z0-9][A-Z0-9_]{0,31}$`), `agent_id` = 플랫폼 `AgentId`(`^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`), `close_ym`·`due_ym` = `Ym`(`yyyyMM`), `event_id`·`last_event_id` = Envelope 핵심의 UUID 정규식. ② 닫힌 값 `CHECK (… IN …)`: 아래 DDL에서 `-- A/B/C` 주석이 달린 컬럼 — v1.2의 12개 + V4(v1.5)의 7개 = **19개**. 값 목록은 그 주석(열거가 없는 9개) 또는 포털 열거(`MonthStatus`·`DataStatus`·`DeferralStatus`·`IngestState`·`IngestEventStatus`·`AgentStatus`·`ReceivableStatus`·`NetBasis`·`ReconSource`·`FlagType`)이고 `StatusEnumDdlTest`가 셋(주석·V1~V4·열거)을 대조한다. `/...`로 끝나는 열린 목록(`comm_type`·`role`)은 `CHECK`가 없다. ③ `notification`의 유일 키는 설계사 안에서(Q1).

**인제스트 표**(v1.4, V3): `ingest_event`는 적용한 이벤트(`APPLIED`)와 키를 믿을 수 있는 독 이벤트(`FAILED`)만 남긴다 — 건너뛴 이벤트는 행이 없다(같은 `eventId`의 행이 이미 있어 PK상 두 번째 행이 불가능하다. 열거의 `SKIPPED`는 **미사용**, 지표 `ingest_events_total{result=skipped}`로만 — Phase 1 승인 Q2). `payload_hash`는 `{type, version, occurredAt, aggregate, payload}`의 JCS SHA-256(`seq`·`eventId`·모르는 최상위 필드 제외 — Q1)이고 payload 본문은 저장하지 않는다.

**RLS**(v1.2): 모든 테넌트 테이블(`tenant` 포함)에 `ENABLE` + `FORCE ROW LEVEL SECURITY`, 정책 `tenant_isolation USING/WITH CHECK (tenant_id = current_setting('app.tenant_id', true))` — 정본 `V2__rls.sql`. 미설정이면 `NULL`이라 오류 없이 0행이고, `tenant`도 자기 행만 보인다. 테넌트 설정은 platform-spring의 `TenantSessionBinder`가 트랜잭션 시작 때 `SELECT set_config('app.tenant_id', ?, true)`로 넣는다(트랜잭션 로컬 — `SET LOCAL`과 같은 효과). 설정 이름은 공개 상수 `TenantSession.SETTING_NAME`이고 `RlsSettingNameTest`가 마이그레이션 문자열과 대조한다(철자가 틀리면 정책이 늘 `NULL`을 읽어 조용히 0행이 되기 때문). 앱 롤은 RLS를 우회할 수 없는 일반 롤이고, 모든 포털 롤이 `NOBYPASSRLS`·`NOSUPERUSER`임을 V2가 단언한다(§9 롤 표). 마이그레이터도 정책을 따르므로(`FORCE`) **데이터 마이그레이션(백필·재구축 스왑)은 테넌트를 열거하며 테넌트마다 `set_config('app.tenant_id', …, true)`로 설정한 뒤 실행한다** — 설정 없이는 0행을 보고 쓰기는 `WITH CHECK`에 거부된다(Phase 0 수용 심사 B1, §6.7 재구축 설계 때 다시 본다).

**불변식(테스트로 상시 검증)**
- `earnings_month.gross/clawback_offset/adjustment = Σ earnings_line` (테넌트·설계사·월 단위).
- 원장(v1.5 — 엔진 `LimitLedger.post` 규칙, **DD-8**): **양수 전기 뒤** `accum_after ≤ limit_amount`, 모든 전기 뒤 `accum_after ≥ 0`, `accum_after − 직전 accum_after = amount`, `postingSeq` = 직전 + 1. 재산정(`LimitLedgerRebased`)은 누적을 바꾸지 않고 검사도 없다 — 감액 재산정 뒤에는 `accum_paid > limit_amount`가 정상이다(부록 A-3). 위반 시 이벤트 적용 실패 → 인제스트 정지, 엔진 이상 신호.
- `status`가 CONFIRMED/PAID인 월의 라인은 이후 이벤트로 변경되지 않는다(변경 시도 → 인제스트 정지 + 운영 알림).

## 6. 핵심 로직

### 6.1 인제스트 규약

(v1.4 — Phase 1 지시문 D-1~D-5, 계획 ③·④·⑤, 승인 Q1~Q7. 정본 코드: `portal-domain` `IngestTransitions`·`IngestErrorCode`, `portal-ingest` `IngestApplier`·`IngestWorker`·`EnvelopeValidator`·`PayloadHasher`)

- **테넌트별 단일 워커**(순서 보장). 회차: tx₀에서 커서를 읽고(없으면 `RUNNING`·0으로 만든다) `RUNNING`이 아니면 끝 → 피드 호출(트랜잭션 밖, `afterSeq = last_seq`) → 이벤트마다 **하나의 DB 트랜잭션**: `pg_try_advisory_xact_lock`(못 잡으면 다른 인스턴스가 처리 중 — 회차 끝) → 커서 다시 읽기(판정은 이 트랜잭션 안의 값으로만) → 수신 검증 → 해시 → 기존 행 대조 → seq 규칙 → `ingest_event` → 프로젝터 → `ingest_cursor`. 한 건이 멈추면 그 건에서 끝나고 앞선 건은 커밋된 채다. 적용 실패 뒤 백오프 없음 — 멈추는 것이 규약.
- **멱등 키·해시**: `(tenant_id, event_id)`, `payload_hash` = JCS SHA-256(`{type, version, occurredAt, aggregate, payload}` — `seq`·`eventId`·모르는 최상위 필드 제외). 같은 eventId·같은 해시·같은 seq → **건너뜀**(행·커서 불변, 지표만).
- **seq 규칙**: 기대값 `last_seq+1`보다 작고 아는 eventId면 건너뜀, 작고 **처음 보는** eventId면 독(과거 번호의 새 사실은 발행자 이상), 같으면 적용, 크면 갭 → 정지(`FAILED`). 엔진은 커밋된 행에만 갭 없이 번호를 붙인다(엔진 설계서 §6.8) — 갭은 결함 신호다.
- **독 이벤트**: 판정 순서와 기록. 본 트랜잭션은 롤백되고 `FAILED` 행(키를 믿을 수 있을 때)과 커서 정지는 **별도 트랜잭션**에 쓴다. 다른 테넌트는 영향 없다(워커 전체 상태는 없다).

  | # | 판정 | code | 커서 | `ingest_event` |
  |---|---|---|---|---|
  | 0 | 응답 `tenantId` ≠ 테넌트 | `TENANT_MISMATCH` | FAILED | 없음 — 아무것도 적용하지 않는다 |
  | 1 | Envelope 핵심 위반 | `SCHEMA_VIOLATION` | FAILED | 없음 — 키를 믿을 수 없다 |
  | 2 | `version` > 지원 최대(포털 Envelope 스키마의 `version.const`) | `UNSUPPORTED_VERSION` | **PAUSED** | 없음 |
  | 3 | `type` ↔ `aggregate.kind` 짝(포털 Envelope 스키마의 `if/then`에서 읽는다) | `TYPE_KIND_MISMATCH` | FAILED | FAILED 행 |
  | 4 | 포털 Envelope·payload 스키마 위반 | `SCHEMA_VIOLATION` | FAILED | FAILED 행 |
  | 5 | 아는 eventId·다른 해시 | `HASH_MISMATCH` | FAILED | 없음 — 기존 APPLIED 행을 지킨다 |
  | 6 | 아는 eventId·다른 seq | `EVENT_SEQ_CONFLICT` | FAILED | 없음 |
  | 7 | 처음 보는 eventId·seq < 기대값 | `PAST_SEQ_NEW_EVENT` | FAILED | FAILED 행 |
  | — | 처음 보는 eventId·seq > 기대값 | `SEQ_GAP` | FAILED | 없음 — 결함은 빠진 쪽 |
  | 8 | 프로젝터 예외 | `PROJECTOR_ERROR` | FAILED | FAILED 행 |
  | 9 | 그 밖의 적용 트랜잭션 오류(DB 제약 위반 등 — 분류하지 못한 것) | `APPLY_ERROR` | FAILED | 없음 |

  `FAILED` 행이 있는 eventId가 재개 뒤 다시 오면 처음 보는 것으로 다시 판정하고, 적용되면 그 행이 `APPLIED`가 된다. `error`는 `{code}: {detail}`이고 detail에는 seq·eventId·기대값·스키마 위치·키워드·예외 이름만 — payload 값·토큰·DB 메시지는 쓰지 않는다.
- **피드 실패**: 401 → `PAUSED(FEED_UNAUTHORIZED)`, 토큰 파일이 없거나 비면 폴링 전에 `PAUSED(TOKEN_MISSING)`, 422 → `FAILED(AFTER_BEYOND_HEAD)`, 네트워크 오류·5xx·시간 초과·형식 오류 → 상태 불변(다음 주기에 다시, `ingest_feed_errors_total`).
- **상태 기계**(표에 없는 조합은 거부): `RUNNING` —적용·건너뜀·일시 실패→ `RUNNING`, —데이터 결함→ `FAILED`, —판·설정 문제·운영자 pause→ `PAUSED`; `FAILED`·`PAUSED` —운영자 resume→ `RUNNING`; `REBUILDING`은 재구축(§6.7, Phase 2)이 정한다. 정지된 테넌트는 화면에 "데이터 동기화 지연" 배너를 띄운다(마지막 동기 시각 표시).
- **스케줄**(v1.4): 1초 틱마다 테넌트 목록(전용 롤 `portal_directory`, §9)을 돌며 주기가 된 테넌트의 회차를 하나씩 돌린다. `tenant.status`가 `ACTIVE`가 아니면 폴링하지 않는다. 한 테넌트의 예외는 그 테넌트에만 남는다. 주기는 `tenant.params.poll_interval_seconds`(5~30, 없거나 범위 밖이면 전역 기본 — 기본 키 집합 §14.0에는 더하지 않는다). 폴링은 `portal.ingest.enabled`일 때만 돈다(기본 꺼짐 — 배포 구성이 켠다). 서비스 토큰은 테넌트별 파일 `<token-dir>/<TENANT_ID>`(소유자 밖에서 읽을 수 있으면 기동 뒤 첫 사용 때 경고).
- **운영 명령**(v1.4, `portal-app` `cli` 프로파일 — 웹·폴링 없이 명령 하나, 종료 코드 0 성공·2 거부·64 사용법): `ingest status [--tenant=T]`, `ingest resume --tenant=T --from-seq=n`(`FAILED`·`PAUSED` → `RUNNING`, 커서를 n에 — n은 마지막 `APPLIED` seq 이하만, 건너뛰기는 재구축으로만), `ingest pause --tenant=T`(`RUNNING` → `PAUSED(OPERATOR_PAUSE)`), `ingest rebuild --tenant=T`(v1.5 — §6.7, 종료 코드 1 = 재구축 실패). 행위자는 실행한 OS 사용자(`user.name`) 하나 — v1.6에서 `--actor`는 없어졌다(쓰면 64). 전 건 `audit_access`에 같은 트랜잭션으로 — 거부도(`INGEST_STATUS`·`INGEST_RESUME`·`INGEST_RESUME_REJECTED`·`INGEST_PAUSE`·`INGEST_PAUSE_REJECTED`, v1.5 `INGEST_REBUILD`·`INGEST_REBUILD_REJECTED`·`INGEST_REBUILD_SUCCEEDED`·`INGEST_REBUILD_FAILED` — 재구축은 트랜잭션마다 한 행, `actor_subject` = `cli:<actor>`, `target` = `cursor:<T>@<n>`). 행위자가 없으면 감사할 수 없으므로 DB에 닿기 전에 거부한다. **인가**(v1.6 — 포털 Phase 3 D-9): `cli:<OS 사용자>`가 **그 테넌트의** `identity_link`에 `OPERATOR`·`ACTIVE`로 있어야 한다(명령마다 테넌트마다 먼저 확인). 아니면 `T not authorized` + 종료 코드 2, 그 테넌트에 `AUTHZ_DENIED`(detail `NO_LINK`·`REVOKED`·`ROLE`, target `cli:ingest <명령>`). 테넌트를 지정하지 않은 `status`는 테넌트마다 확인하고 하나라도 거부면 2. 등록·해제는 운영 SQL(`docs/운영.md` §3). 운영 호스트 접근 통제는 여전히 첫 문이다.

### 6.2 상태 매핑 (엔진 → 화면)

| 엔진 사실 | `earnings_month.status` | `net_basis`(v1.5) | 화면 라벨 | 세후 표시 |
|---|---|---|---|---|
| 라인만 존재 | PROVISIONAL | NULL | **예상** | "세후는 야간 산출 후 표시" |
| `StatementEstimated` 수신 | ESTIMATED | ESTIMATE | **예상** (기준 시각 `estimate_as_of` 표시) | 예상 원천세·예상 실수령. 기준 seq(`estimate_basis_seq`)는 하한 — 그 뒤 라인이 와도 상태는 ESTIMATED 그대로 |
| `StatementConfirmed` 수신 | CONFIRMED | 세액이 실려 오면 CONFIRM, 아니면 이전 값 유지(ESTIMATE 또는 NULL) | **확정** — `net_basis = ESTIMATE`이면 "확정(세후 예상)" | 엔진 v1은 마감 이벤트에 세액·순액을 싣지 않는다 — 예상 값을 그대로 둔다 |
| `PayoutCompleted` 수신 | PAID | PAYOUT | **지급완료** (지급일) | 확정 원천세·실지급액(`paidAmount` = `net`), 지급 런 확정값 `payable`·`receivable_offset`·`carried_receivable`·`run_seq` |

상태 전이는 위 순서뿐이다(v1.5 — `MonthTransitions`): 마감월(CONFIRMED·PAID)의 라인·예상·두 번째 확정과 PAID의 두 번째 지급은 독(`CLOSED_MONTH`), 확정 전의 지급은 독(`STATE_MISMATCH`). 라인 없는 달도 확정이 행을 만든다(정정만 있는 설계사 — 엔진 E1 수용 Q1). 마감·지급 이벤트의 합계가 포털 합산과 다르면 독이 아니라 그 달 `data_status = DRIFT` + `recon_result(source EVENT)`(§6.6).

**화면 라벨**(v1.7 — 포털 Phase 4, Phase 3 수용 심사 Q1·Q2): 문구는 `web/src/messages.ko.json`(데이터), 표는 `web/src/labels/labels.ts`. 모든 금액은 라벨과 함께만 그려진다(`<Amount value label>` — 라벨 없는 금액은 타입 오류). 세전·환수 상계·정정·라인 금액의 라벨은 월 상태(예상·예상·확정·지급완료). 세후(실수령)는 아래 16칸(계약 열거 4 × `netBasis` 3 + 없음 — `labels.test.ts` 전수):

| 월 상태 | `netBasis` | 세후 |
|---|---|---|
| PROVISIONAL | 없음 | 숨김 — "세후는 야간 산출 후 표시"(세전을 크게) |
| ESTIMATED | ESTIMATE | **예상** + "기준 {estimateAsOf}" |
| CONFIRMED | ESTIMATE | **예상**(잠정 명세 값 — 세전은 "확정") |
| CONFIRMED | 없음 | 숨김 — "세후는 지급 시 확정" |
| CONFIRMED | CONFIRM | 확정 |
| PAID | PAYOUT | **지급완료** + 지급일 |
| 그 밖의 10칸 | | 숨김 — "세후 정보 없음"(계약상 오지 않는 조합 — 보이지 않는 쪽으로 실패) |

원천세는 세후가 보일 때만 그 라벨로. 원장 금액(한도액·누적·잔여·삭감)은 "원장 기준", 월납 보험료는 "계약 정보", 분급·채권 금액은 그 항목의 상태, 지급 런 확정값은 PAID 달에만 "지급완료".

| 분급 상태 | 화면 라벨 |
|---|---|
| SCHEDULED | 예정 |
| RELEASED | 이번 달 지급 대상 |
| HELD | 보류 — 사유 표시(예: 해당월 유지 조건 미충족) |
| CANCELLED | 취소 — 사유 표시(해약·실효 등) |

분급 전이(v1.5 — 엔진 `ScheduleEntry` 그대로, **DD-9**): SCHEDULED → RELEASED(`DUE_RELEASED`)·HELD(`POLICY_NOT_INFORCE`)·CANCELLED(`POLICY_TERMINATED`·`SOURCE_REVERSED`), HELD → CANCELLED. **HELD → RELEASED는 없다**(엔진이 거부한다 — 이전 판의 그림은 틀렸다). 저장된 상태가 이벤트의 `from`과 다르거나 사유 짝이 틀리면 독(`STATE_MISMATCH`).

라인의 `reversal_of_calc_id`가 있으면 원본 라인은 "취소됨"으로 접히고 음수 라인과 짝지어 표시한다. 합산에는 둘 다 포함된다(엔진과 동일 규약).

### 6.3 한도 뷰 규칙

- `remaining = limit_amount − accum_paid`, `utilization = accum_paid / limit_amount`(표시용 소수 1자리, 저장하지 않음).
- 경고 단계: `utilization ≥ limit_warn_pct` → WARN, `≥ limit_crit_pct` → CRITICAL, `remaining = 0` → FULL. 임계치는 테넌트 파라미터.
- 삭감/이연: `earnings_line.limit_cut_amt > 0`인 라인을 계약별로 합산해 `cut_total`(CUT)·`deferred_total`(DEFER_AFTER_FY)로 표시하고, 이연분은 `deferral_item(reason=LIMIT_DEFER)`와 연결한다. 합산은 `CommissionCalculated`를 적용할 때 그 원장 행에 저장한다(v1.5 — 정수 합산). **현재 엔진은 `DEFER_AFTER_FY`도 실제로는 삭감한다(엔진 E1-1)** — `deferred_total`은 계약의 정책값을 따른 분류일 뿐이다. 화면 문구(v1.7 — Phase 3 수용 심사 Q4): 정책 이름이 아니라 사실대로 **"한도 초과 삭감"**, `DEFER_AFTER_FY`에는 보조 문구 "(사규: 초년도 후 이연 — 현재 이연 스케줄 없음)". 두 합계를 더하지 않고 0이 아닌 것만 각각 보인다. 엔진이 이연을 구현하면 문구만 바뀐다.
- 2026-07-01 이전 체결 계약은 엔진이 원장을 열지 않으므로 화면에 "한도 미적용 계약(체결일 기준)"으로 표시한다. 이 분기는 포털이 판단하지 않는다 — 원장 이벤트가 없다는 사실로만 표시한다.
- `fy_end`까지 남은 일수, 재산정(REBASE) 이력, 계약 상태 배지(`policy_flag`)를 함께 보여준다.
- `REINSTATE`(엔진 REVIVE)가 열린 플래그 없이 오면 독이 아니라 아무것도 하지 않는다(v1.5 — Phase 2 수용 심사 Q6: 엔진이 실효 없이 부활을 낼 수 있는지 확인되지 않아 보수적으로 받는다).

### 6.4 분급 전망 규칙 (포털이 하는 유일한 "계산"의 경계)

- 기본 전망 = 월별 `Σ deferral_item.amount where status ∈ {SCHEDULED, RELEASED}`. HELD는 별도 색으로 표시, CANCELLED는 제외.
- v1.5(Phase 2): HELD는 다시 RELEASED가 되지 않는다(엔진 전이 — §6.2, **DD-9**) — HELD 금액은 "다시 받을 수 있는 돈"으로 보이지 않게 Phase 4 화면 문구를 정한다. `reason = LIMIT_DEFER`(한도 이연) 항목도 같은 합계에 들어간다(`CURVE`와 상태 규칙이 같다). Phase 2는 `deferral_item` 행만 만들고, 합계·토글은 Phase 4 조회에서.
- **시나리오 토글**: "전건 유지"(기본) / "유지율 가정 p%" — 월별 합계에 p를 곱해 표시. 기능은 v1에 구현하되 **테넌트 파라미터 `forecast_scenario_enabled`가 기본 false**이므로(확정, §14.0) 화면에서 토글이 노출되지 않고 API도 `scenario=RETENTION` 요청을 400으로 거부한다. 활성화한 테넌트에서는 "비확정·참고" 문구가 고정된다. 구현은 `ForecastScenario` 한 클래스에 격리하고, 이 클래스 외부에서 금액에 비율을 곱하는 코드는 아키텍처 테스트로 금지한다.
- 계속(유지)수수료는 엔진에 스케줄이 없으므로 전망에 포함하지 않는다. 화면에 "분급 확정 스케줄만 반영" 문구를 둔다.
- 2027 분급제의 상품군별 적용 여부(일부 상품 제외 가능성 보도)는 엔진 커브 데이터가 결정한다. 포털은 `deferral_item`이 있으면 보여주고 없으면 보여주지 않을 뿐이다.

### 6.5 알림 규칙

알림은 프로젝터 적용과 **같은 트랜잭션**에서 파생되며 `dedup_key`로 중복을 막는다. **`dedup_key`는 설계사 안에서 유일**하다(v1.2 Q1 — 유일 키 `(tenant_id, agent_id, dedup_key)`; 아래 키 문자열에는 설계사를 넣지 않는다, 컬럼이 이미 있다).

| 트리거 이벤트 | 조건 | dedup_key | 심각도 |
|---|---|---|---|
| `LimitLedgerPosted` | utilization이 WARN/CRIT/FULL 경계를 **상향 통과** | `LIMIT_{LEVEL}:{ledgerId}` | INFO/WARN/CRIT |
| `CommissionCalculated` | `limitCutAmt > 0` | `LIMIT_CUT:{calcId}` | WARN |
| `LimitLedgerRebased` | 항상 | `LIMIT_REBASE:{ledgerId}:{postingSeq}` | INFO |
| `CommissionCalculated` | commType=CLAWBACK | `CLAWBACK:{calcId}` | WARN |
| `DeferralStatusChanged` | to ∈ {HELD, CANCELLED} | `DEFER_{to}:{scheduleId}` | WARN |
| `PolicyEventObserved` | PAYMENT_OVERDUE/LAPSE/CANCEL | `POLICY_{type}:{policyNo}:{occurredOn}` | WARN |
| `StatementConfirmed` | 항상 | `STMT_CONFIRMED:{ym}` | INFO |
| `PayoutCompleted` | 항상 | `PAYOUT:{ym}` | INFO |
| 이의제기 답변 | status→ANSWERED | `INQUIRY:{inquiryId}` | INFO |

같은 날 같은 타입이 다수 발생하면 하루 1건의 다이제스트로 묶는 옵션(테넌트 파라미터). 채널은 v1 인앱, 이후 푸시·알림톡은 `NotificationChannel` 어댑터 추가.

### 6.6 대사(Recon)와 DRIFT

- **첫 지점은 이벤트 대사**(v1.5, Phase 2 지시문 D-3): `StatementConfirmed`·`PayoutCompleted`를 적용할 때 그 달 포털 합산(gross/offset/adjustment)과 이벤트의 엔진 합계를 비교한다. 다르면 **독이 아니다** — 이벤트는 적용되고(인제스트는 멈추지 않는다) 그 달 `data_status = DRIFT`, `recon_result`에 `source = EVENT`·`source_seq` = 이벤트 `seq`인 한 행(`ON CONFLICT DO NOTHING` — 재구축·재적용이 같은 행을 다시 넣어도 한 행, 승인 Q2), 지표 `projection_drift_total`. 이벤트에 없는 합계 필드는 비교하지 않는다(엔진 필드가 선택인 것 — 계약 v1.1). 같으면 행을 남기지 않는다. `engine_net`은 그 이벤트의 `net`(없으면 NULL). 한 번 `DRIFT`인 달은 뒤 이벤트가 일치해도 `DRIFT`로 남는다(복구는 아래 재구축·재대사).
- 아래 야간 대사는 `source = BATCH`(`source_seq` = 0)로 Phase 7에서 붙는다.
- 매일 새벽 테넌트별로 활성 설계사 전원에 대해 당월(ESTIMATE)·직전 마감월(CONFIRMED) 명세를 엔진에서 페이지 단위로 조회하고 `earnings_month`의 포털 합산(gross/offset/adjustment)과 비교한다.
- 불일치 → `recon_result=DRIFT`, `earnings_month.data_status=DRIFT`. 화면은 해당 월 카드에 "확인 중" 배지를 붙이고 금액을 **흐리게** 표시한다(v1.7: 계약 열거의 `REBUILDING`도 같게 — 색만 연하게 + 점선 밑줄, AA 대비 유지. 틀릴 수 있는 숫자를 확정처럼 보여주지 않는다).
- 자동 복구(Phase 7): 해당 테넌트 재구축(§6.7) → 재대사 → 일치하면 `REPAIRED`. 여전히 불일치면 운영 알림(엔진 측 정정 가능성). 재구축은 원자적이라(실패하면 아무것도 바뀌지 않는다) 그림자 스키마·스왑이 필요 없다(v1.5).

### 6.7 재구축(Rebuild)

v1.5(Phase 2 지시문 D-11, 계획 ⑥·승인 Q10): **그림자 스키마가 아니라 한 트랜잭션 재생.** 뷰 표가 테넌트 공유(멀티테넌트)라 `RENAME` 스왑이 불가능하고, PostgreSQL MVCC가 "재구축 중에도 기존 행으로 조회"를 준다. DDL이 없으니 FORCE RLS·`portal_migrator` 문제도 없다. `ingest rebuild --tenant=T`(§6.1 운영 명령)는 트랜잭션 셋이다 — 지시문의 "커서 `REBUILDING` → 한 트랜잭션 안에서 재생"은 같은 트랜잭션의 `REBUILDING`이 커밋 전까지 아무에게도 보이지 않아 상태가 장식이 된다(**DE-9**).

1. **txA**: 테넌트 잠금(`pg_try_advisory_xact_lock` — 워커와 같은 키, 못 잡으면 거부·감사) → 커서 상태가 `OPERATOR_REBUILD`를 받는지(`RUNNING`·`PAUSED`·`FAILED`만) → `REBUILDING` 커밋. 이후 워커는 폴링하지 않고(적용기도 트랜잭션 안에서 `NOT_RUNNING`), `resume`·`pause`·`rebuild`는 거부된다.
2. 피드 첫 페이지(`afterSeq=0`)의 `headSeq` > `portal.ingest.rebuild.max-events`(기본 50,000)면 시작하지 않고 txC.
3. **txB**(한 트랜잭션 — 원자성): 잠금(txA 직전에 `RUNNING`을 읽은 워커의 적용 트랜잭션이 잠깐 쥘 수 있어 짧게 재시도) → 뷰 8표 DELETE(`agent_profile`·`earnings_line`·`earnings_month`·`policy_limit`·`policy_limit_history`·`deferral_item`·`clawback_item`·`policy_flag`) → seq 1부터 2의 `headSeq`까지 재생(재생 중 늘어난 머리는 따라가지 않는다 — 상한이 txB 길이를 묶는 전제, 나머지는 `RUNNING`이 된 커서에서 워커가 이어 받는다. 재생 수가 상한에 닿으면 실패 — 이중 방어. 그 `headSeq`가 이미 `APPLIED`인 최대 seq보다 작으면 지우기 전에 실패하고, 피드가 그 seq에 닿기 전에 끝나도 실패한다 — 커서가 `APPLIED` 행 아래에 서면 워커가 그것들을 아는 이벤트로 건너뛰어 뷰에서 영영 빠진다) — 적용기와 **같은 판정**(`EventCheck`: 수신 검증·해시·기존 `APPLIED` 행 대조·seq 규칙), 이미 `APPLIED`인 행은 해시·seq가 같아야 하고 같으면 프로젝터를 다시 부른다, 없거나 `FAILED`면 `APPLIED`로 → 전수 불변식(월 합계 = Σ 라인 — 라인이 있는데 월 행이 없는 것 포함, 원장 누적 = Σ 전기, 전기 연쇄 `accum_after − 직전 = amount`) → 커서 `RUNNING`·`last_seq`·`last_event_id` = 재생한 마지막 → 커밋.
4. 실패(독·해시 불일치·seq 불연속·불변식·피드 오류·상한): txB 롤백(뷰·`ingest_event`·`recon_result` 전부 원래대로) → **txC** 커서 `FAILED(REBUILD_FAILED: {원인} seq n)`, `last_seq`는 그대로. 원인을 고친 뒤 `FAILED`에서 다시 재구축할 수 있다.

- **지우지 않는 것**: `ingest_event`(해시 대조의 기준)·`ingest_cursor`·`audit_access`·`recon_result`(DRIFT 이력 — 재생이 같은 행을 다시 만들어도 `ON CONFLICT DO NOTHING`), 사용자 데이터(`tenant`·`identity_link`·`notification`의 읽음 상태·`inquiry`·`simulation_log`).
- **스트림 출처**: 피드에서 다시 받는다 — 포털은 payload를 저장하지 않는다(Phase 1 D-1). 피드 호출이 txB 안에 있다(긴 트랜잭션 — §14.1 #11).
- 알림 파생(§6.5)은 재생에서 부르지 않는다 — Phase 6에서 정한다(§14.1 #12).
- 감사: 시작·거부·성공·실패가 각 단계의 트랜잭션 안에서 한 행씩. 지표 `ingest_rebuild_seconds{outcome}`.
- **결정론**(D-12): 같은 스트림 → 뷰 9표(`recon_result` 포함, 테넌트 컬럼 제외, `source_seq`·`last_seq` 포함)·`ingest_event`·`ingest_cursor`가 ① 한 번에 ② 중간 재시작 ③ 한 번에 + 재구축에서 바이트 동일(`IngestDeterminismIT`).

## 7. 조회 API (포털 → 웹)

self 엔드포인트의 경로에는 `agentId`가 **없다**. 설계사 식별은 토큰 subject → `identity_link` 조회로만 이뤄지며, 이는 IDOR를 구조적으로 제거한다. 조회 저장소(`AgentQueryRepository`)의 **모든 문장**은 `agent_id = :agentId`를 가진다(조인의 각 표 포함 — SQL 스캔의 두 번째 술어). 정본 계약은 `contracts/api/v1/portal-api.openapi.yaml`(v1.6 — 포털 소유, 웹 Phase 4가 클라이언트를 생성)이고 모든 시험 응답이 그 계약으로 검증된다.

| 메서드/경로 | 응답 요약 |

모든 응답 공통 필드: `asOf: {seq, at}`(커서 `last_seq`·`updated_at` — 커서가 없으면 `seq` 0, `at` 생략), `dataStatus: OK|SYNC_DELAYED`(**동기화** 상태 — 커서 상태 ≠ `RUNNING`, `caught_up_at` 없음, `now − caught_up_at > sync_delay_seconds` 중 하나면 지연; 재구축 중에도 지연). 월 응답은 그 달의 **대사** 상태를 `monthDataStatus: OK|DRIFT`로 따로 준다 — v1.5까지 한 필드 `dataStatus: OK|DRIFT|SYNC_DELAYED`가 두 뜻을 섞었다(v1.6 **DD-12**). 금액은 정수 원, 통화 포맷은 프론트 담당. 선택 필드는 값이 없으면 빠진다(`null`을 보내지 않는다).

**증권번호는 어느 응답에도 없다**(v1.6): `policyMasked`(끝 4자 외 `*`)와 `policyKey` = HMAC-SHA256(배포 비밀 파일 `portal.query.policy-key-secret-file`, `tenant_id` + `U+001F` + `policy_no`)의 앞 16자 16진. 비밀 없는 해시는 증권번호 형식이 좁아 열거로 되돌아간다(**DE-15**). 키 → 원문은 요청 안에서 **그 설계사의** 증권번호 집합으로만 푼다(SQL에 키 없음 — 남의 키는 빈 결과). 비밀을 회전하면 모든 키가 바뀐다 — 화면은 키를 저장하지 않는다(`docs/운영.md`). 피보험자는 엔진이 가린 `insuredMasked` 그대로.

**거부·형식**(v1.6, §9): 인증 실패는 전부 같은 401, 링크 없음·`REVOKED`·역할(`MANAGER`·`OPERATOR`)·남의(없는) 자원·없는 경로·메서드 불일치·경로 변수 형식 오류(`ym`·키)는 전부 같은 404, 쿼리 파라미터 형식·범위 오류만 400 `INVALID_REQUEST`. 본문은 `application/problem+json` `{code, message}`.

**캐시**(v1.6, §10): 200은 `Cache-Control: private, no-cache`(`no-store` 아님 — 304가 의미를 갖게)와 약한 ETag `W/"<seq>.<sync>.<cfg>"`(`sync` = `O`/`D`, `cfg` = 그 응답이 실제로 읽은 테넌트 설정 — 지급일 규칙·임계치·지연 초 — 의 SHA-256 앞 8자; 라인 목록은 뒤에 `.<page>.<size>.<필터 해시 8자>`). 같은 `seq`에서도 지연 상태·설정이 바뀌면 ETag가 바뀐다(**DE-16**). `If-None-Match`는 소유 확인 뒤에만 비교한다(남의 자원은 304가 아니라 404).

## 8. 화면 설계 (모바일 우선, 텍스트 와이어)

**공통**: 상단에 동기화 상태 칩(`기준 09-22 10:15` / `동기화 지연` / `확인 중`). 모든 금액 옆 상태 라벨(예상·확정·지급완료). 원 단위 정수, 천 단위 구분.

**구현 규약**(v1.7 — 포털 Phase 4, `web/`):
- 경로(닫힌 목록 `web/src/routes.ts` = 서버 `ScreenConfiguration.SCREEN_PATHS`): `/`, `/statements`, `/statements/{ym}`, `/lines/{calcId}`, `/limits`, `/limits/{ledgerId}`. 경로에 증권번호·`policyKey`는 없다.
- **이번 달** = 브라우저 시계의 KST 달력 월(시간대 명시). 그 달 행이 없으면(404) "이번 달 내역이 아직 없습니다" — `/me` 404만 "등록되지 않은 사용자"다(같은 404 바이트). 전월 대비·다음 달 분급 예정액은 보이지 않는다(CR-1·Phase 5). 최근 알림은 비활성 진입점만(빈 상태 문구 없음 — 알림이 있는지 모른다). 주의 계약 = 단계 ≠ OK인 원장 수, 납입 지연·실효 = `OVERDUE`·`LAPSED` 플래그 수(`/limits?status=ALL` 한 콜 — `status=WARN`은 정확히 WARN만).
- 동기화 칩: 화면에 그려진 응답들을 나쁜 쪽으로 합친다 — 하나라도 `SYNC_DELAYED`면 "동기화 지연 — 기준 {MM-DD HH:mm}", 기준은 가장 작은 `seq`의 `at`(KST), `at`이 없으면 "동기화 전".
- 명세: 월 목록은 36개월 중 행이 있는 달. 라인은 그 달 전체를 받아(페이지를 `total`까지) **같은 달 짝만** 접는다(원 라인은 "취소된 원 라인 보기" 아래). 다른 달 짝은 접지 않고 "취소됨 → {월}"·"취소 ← {월}" 배지 + 상대 달 링크. 지급 런 값(지급액·채권 상계·이월 채권)은 PAID 달에만. 예상 이월 채권은 보이지 않는다(§14.1 #13).
- 정정만 있는 확정 달(라인이 없거나 `ADJUSTMENT`뿐, 정정 ≠ 0): "정정 {금액} — 지급 반영은 정산팀 확인"(단정하지 않는다 — §14.1 #12).
- 한도: 주의/전체 필터는 화면에서(단계 문자열). 카드에 상품명·피보험자는 없다(원장 응답에 없다 — CR-4). 소진 바는 `utilization` 문자열을 숫자로 바꾸지 않고 CSS 속성으로. 산식은 "월납 {월납} × {배수}배 → 한도 {한도액}" 표시 문자열(규정 기준일 없음 — CR-3).
- 화면은 금액을 계산·비교·변환하지 않는다 — 불투명 `Won` 타입, ESLint 규칙, 번들 스캔(`CLAUDE.md` 화면 규약). 다크 모드 없음(`color-scheme: light` — 웹뷰의 강제 반전도 끈다), 한국어 하나.

## 9. 보안·개인정보·멀티테넌시

- **인증**: OIDC. 테넌트별 IdP(도입 GA의 SSO) 또는 포털 기본 IdP. 개발·데모는 Keycloak(Phase 8), 시험은 인프로세스 발급기(RSA 키 + JWKS 스텁). **테넌트는 토큰의 `iss`로 정한다**(v1.6): `tenant.oidc_issuer`(UNIQUE, 정확 일치)·`oidc_audience` — 둘 다 NULL이면 로그인 불가 테넌트. 발급자 표는 테넌트를 바인딩하기 **전에** 읽어야 하므로 전용 롤 `portal_issuer`(아래 롤 표)로 요청마다 읽는다(캐시 없음 — 해제가 즉시 효력). `/api/**` 검증 순서(포털 Phase 3 계획 ②, 전부 **같은 401 바이트** `{"code":"UNAUTHENTICATED","message":"authentication required"}` + `WWW-Authenticate: Bearer` — 사유는 지표에만): ① `Authorization: Bearer` 헤더 하나(없음·다른 스킴·둘 이상 → `NO_TOKEN`) ② JWT 형식·문자열 `iss`·`sub`(1~200자) → `MALFORMED` ③ 헤더 `alg` = `RS256`만 → `ALG_NOT_ALLOWED` ④ `iss` → 등록 테넌트 → `ISSUER_UNKNOWN`(등록된 발급자만 메타데이터·JWKS를 받는다 — 토큰이 고른 URL로 나가는 요청 없음) ⑤ 그 발급자의 JWKS로 서명(발급자 URL마다 디코더 하나) → `SIGNATURE`(각주 v1.6.1 — Spring `Jwt`는 `exp ≤ iat`를 생성자에서 거부해 디코더가 같은 예외를 던지므로 그런 토큰의 지표 사유는 `EXPIRED`가 아니라 `SIGNATURE`다. 응답은 같은 401 바이트 — Phase 3 F9) ⑥ `exp`(필수)·`nbf`, 허용 오차 60초, 주입된 시계 → `EXPIRED` ⑦ `aud`에 그 테넌트의 `oidc_audience` → `AUDIENCE` ⑧ `tenant_id` 클레임이 **있으면** 같은 테넌트(교차 검사 — 신뢰 근거가 아니다) → `TENANT_MISMATCH`. JWKS를 받지 못하면 401이 아니라 500(서버 쪽 고장을 토큰 탓으로 감추지 않는다 — 401이면 클라이언트가 재로그인을 되풀이한다), 지표 `api_jwks_failures_total{issuer_hash}`(발급자 URL의 SHA-256 앞 12자, v1.6.1 — Phase 3 F6), 재시도는 클라이언트. 토큰에서 읽는 것은 `iss`·`sub`·`aud`·`exp`/`nbf`·`tenant_id`뿐이고 `roles`·`agent_id` 클레임은 어디서도 읽지 않는다 — `Jwt`를 만지는 포털 클래스는 검증기 하나다. 역할(팀장·지점장 등)도 엔진 이벤트에서 받지 않는다 — 엔진에는 역할 개념이 없고(오버라이드 수급자는 사람이 아니라 조직) `AgentSnapshot.role`은 선택이다(v1.3).
- **화면의 토큰**(v1.7 — 포털 Phase 4 Q1): 웹뷰 호스트가 `/{경로}#token=<JWT>`로 연다. 첫 스크립트가 React보다 먼저 프래그먼트를 메모리로 옮기고 `history.replaceState`로 지운다(프래그먼트는 요청·Referer에 실리지 않는다). 브라우저 저장소·쿠키 0(ESLint + E2E). 새로고침이면 호스트가 다시 넣는다. 토큰이 없거나 401 → "다시 로그인" 화면(포털에는 로그인 화면·IdP 주소가 없다, "다시 시도" = 새로고침), `/me` 404 → "등록되지 않은 사용자 — 소속 GA에 문의". 독립 브라우저(데모)의 OIDC PKCE는 Phase 8. 호스트의 갱신 규약은 §14.1 #14.
- **화면 응답 헤더**(v1.7 — Q2·Q6): 같은 출처, `portal-app`의 화면 체인(인증 없음 — 인증 필터는 `/api` 체인에만). CSP `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`(네이티브 웹뷰는 프레임이 아니다), `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`. 화면 경로는 `index.html`(`no-store`), `/assets/*`는 해시 이름(`immutable`), 그 밖은 같은 404. API 응답 헤더는 v1.6 그대로.
- **인가**: 호출자(`Caller` = 테넌트·`agent_id`·역할)는 `identity_link` PK 조회 1회(캐시 없음)로만 만든다(v1.6). 역할은 닫힌 셋 `AGENT`(설계사 본인 조회)·`MANAGER`(조직 조회 — v2, 지금은 `/api/v1/me/**` 거부)·`OPERATOR`(운영 CLI 주체 — `agent_id` 없음, `/api` 거부). 링크 없음·`REVOKED`·역할 불허·남의(또는 없는) 자원은 전부 **같은 404 바이트** `{"code":"NOT_FOUND","message":"not found"}`이고 사유는 감사(`audit_access` action `AUTHZ_DENIED`, `target` = 경로 템플릿, `detail` = 닫힌 사유 코드 `NO_LINK`·`REVOKED`·`ROLE`·`MISSING` — 값 없음, **본 요청과 별도 트랜잭션**)와 지표에만. `/api`의 없는 경로·메서드 불일치·경로 변수 형식 오류도 같은 404(감사 없음), 쿼리 파라미터 형식 오류만 400 `INVALID_REQUEST` 한 가지. 401에는 감사 행이 없다 — 테넌트를 모르는 요청은 행을 쓸 곳이 없고, 등록된 `iss`만 실은 위조 토큰이 감사 표를 채울 수 있다(쓰기 증폭). self 엔드포인트는 `Caller`의 `agent_id`로만 조회. 조직 조회(v2)는 조직 경로 접두 일치 + 역할 검사, 전 건 `audit_access` 기록. **조직 경로는 출처가 둘이다**(v1.6): `agent_profile.org_path`는 엔진 사실(`AgentSnapshot` — 표시용)이고 `identity_link.org_path`는 포털 사실(운영 등록 — 인가용, v2 조직 조회의 범위). 둘이 달라도 어느 쪽도 고치지 않는다(어느 것을 따를지는 v2 결정 — §14.1 #9).
- **테넌트 격리 3중**: ① 요청 필터가 검증된 토큰 발급자의 테넌트로 `TenantContext`를 바인딩(v1.6), 인증이 없으면 401 ② 저장소 계층은 `TenantScopedRepository`만 허용 — 아키텍처 테스트(ArchUnit + SQL 소스 스캔)로 `tenant_id` 조건 없는 쿼리 금지 ③ PostgreSQL RLS. `TenantContext`·`TenantSessionBinder`·`TenantScopedRepository`는 platform 0.2.0의 것이고(v1.2), 트랜잭션 밖 DB 접근 거부·컨텍스트 없는 트랜잭션 시작 실패는 플랫폼의 보장이지만 포털 시험(`TenantContextGuardTest`·`TenantSessionBinderTest`)으로 다시 증명한다. 직접 접근 허용 목록은 닫힌 FQN 목록 + 전용 롤 + 테넌트 데이터 미접근의 세 조건을 전부 만족해야 하며 Phase 0~2에는 비어 있었다. v1.6(포털 Phase 3)의 첫 항목은 `com.ga.portal.infra.directory.IssuerDirectoryReader` — 발급자 표는 테넌트 설정이고 테넌트 바인딩 전에 읽어야 한다(전용 롤 `portal_issuer`, 그 리더만의 작은 읽기 전용 연결 풀).
- **아키텍처 규칙**(v1.2, `portal-app` `archTest` — 규칙 재료는 platform-core `ArchRules`): (a) 의존 방향 `app → query/ingest/sim/recon → projection → domain → platform-core`, `infra`·`demo`는 `app`만 (b) `domain`·`projection`(과 platform-core)은 Spring·`java.sql`·`javax.sql` 무의존, 플랫폼은 core만 (c) `double`/`float` 전 모듈 금지 (d) DB 접근은 `TenantScopedRepository` 하위 클래스만, 원시 진입점(`DataSource`·`JdbcClient`·`JdbcTemplate`…)은 플랫폼 클래스와 포털 허용 목록만 (e) `platform-spring`은 `infra`·`app`만 (f) platform-core 타입과 단순 이름이 같은 포털 클래스 0 (g) 연결·문장 수준 JDBC 타입(`DataSource`·`DriverManager`·`Connection`·`Statement` 계열)은 플랫폼 클래스와 허용 목록만 — 결과 타입(`ResultSet`)은 `RowMapper` 때문에 (d)가 저장소 하위 클래스까지 허용한다 (h) `BigDecimal` 전 포털 모듈 금지. - **개인정보 최소화**: 포털은 고객 이름을 마스킹 형태로만 저장(엔진이 마스킹해 발행), 주민번호·연락처·주소는 수신하지 않는다. 증권번호는 저장하되 **조회 응답에는 원문이 없다**(v1.6 — `policyMasked` 끝 4자·`policyKey` HMAC, §7). 로그·지표에는 subject·`agent_id`·발급자 URL을 해시(SHA-256 앞 12자)로만, 지표 태그는 `tenant`·`reason`뿐(예외 하나: JWKS 장애 지표의 `issuer_hash` — 발급자 URL 해시, v1.6.1). 저장소 암호화(디스크·백업), 전송 TLS.
- **보존**: 알림 1년, 시뮬레이션 로그 3년(예시값, 테넌트 파라미터), 감사로그 5년(예시값). 라인·명세는 엔진 보존 정책에 종속(재구축 가능하므로 포털 자체 보존은 운영 편의 기간으로 축소 가능).
- **서비스 간 인증**: 포털→엔진은 서비스 토큰(운영 mTLS). 엔진 `/internal/**`는 포털 네트워크에서만 접근.
- **레이트 리밋**: 시뮬레이션·온디맨드 명세 갱신은 설계사당 분당 N회(파라미터). 초과 시 마지막 결과 재표시.

## 12. 구현 로드맵 (Claude Code 작업 순서)

각 Phase는 독립 머지 가능해야 하며 완료 기준을 테스트로 증명한다. `E-`는 엔진 저장소 작업.

- **Phase 0 — 골격**: 저장소·Gradle 모듈·Flyway·Testcontainers(PostgreSQL)·`Won`/`Ym`/`TenantId` 값객체·`TenantContext`·RLS 세션 바인딩·아키텍처 테스트·`contracts/` 초기 스키마. *완료 기준: tenant 조건 없는 저장소 메서드가 테스트에서 실패, RLS 미설정 세션에서 0행.*
- **Phase E1 — 엔진 아웃박스·피드**: §4.4 1·2·5·6 + 4의 이벤트 피드(v1.3 — 포털 Phase 1이 실 공급자 없이 끝나지 않게 E2에서 앞당겼다). *완료 기준: 엔진 골든 시나리오 실행 시 발행 이벤트 시퀀스가 스냅샷 파일과 일치, 스키마 검증 통과.*
- **Phase 1 — 인제스트**: poller·커서·멱등·seq 규칙·독 이벤트 격리·재처리 명령. *완료 기준: 중복/역순/갭/재시작/테넌트 간 격리 테스트 통과.* (v1.4: 엔진 E1과 병렬로 — 피드는 스텁 서버·파일 어댑터로 시험, 실 엔진 대조는 E1 수용 뒤 E2E 1건)
- **Phase 2 — 프로젝션**: earnings·limit·deferral·clawback·flag 프로젝터, 불변식, 재구축, 결정론. *완료 기준: 부록 A 시나리오 이벤트 스트림 → 뷰 골든 테스트, replay 2회 동일.*
- **Phase 3 — 조회 API·인증·인가**: `/api/v1/me/**`, `identity_link`, IDOR 테스트(타인 calcId 조회 404), 감사로그. *완료 기준: 인가 매트릭스 테스트 전건 통과.*
- **Phase 4 — 프론트 1차**: 홈·월별 명세·한도 현황, 동기화 상태 칩, 상태 라벨 규약(v1.7: 알림함은 Phase 6 — 진입점만). *완료 기준: Playwright 시나리오(예상→확정→지급완료 전이 표시).*
- **Phase E2 — 엔진 동기 API**: §4.4 3·4(야간 `StatementEstimated`, 시뮬레이션 2종 dry-run, 명세 조회 — 피드는 E1). *완료 기준: dry-run이 원장·COMM_CALC에 아무 것도 남기지 않음을 테스트.*
- **Phase 5 — 시뮬레이션·분급 타임라인**: `portal-sim`, `simulation_log`, 시나리오 토글(`ForecastScenario` 격리 테스트). *완료 기준: 엔진 응답 스텁으로 계약 테스트, 고정 문구 렌더 테스트.*
- **Phase 6 — 알림 파생·이의제기**: §6.5 규칙, dedup, 다이제스트, inquiry API. *완료 기준: 경계 상향 통과 시 1회만 발생, 하향·재상향 케이스.*
- **Phase 7 — 대사·DRIFT·관측성**: §6.6, 지표·트레이스, 운영 알림. *완료 기준: 인위적 라인 누락 주입 → DRIFT 감지 → 자동 재구축 → REPAIRED.*
- **Phase 8 — 데모 테넌트·통합 실행**: 부록 B 생성기, docker compose, README(포트폴리오 관점), E2E. *완료 기준: `docker compose up` 후 데모 설계사로 로그인해 5개 화면 모두 데이터 표시.*
- **Phase 9 (후속)** — 조직장 뷰, PDF 명세, 푸시/알림톡, 오프라인 스냅샷.

Claude Code에 지시할 때 각 Phase 프롬프트에 반드시 포함할 것: ① 본 설계서 해당 섹션, ② "포털은 금액을 계산하지 않는다(합산·비율 표시만), double 금지, tenant_id 없는 접근 금지, agent_id는 identity_link로만 해석, 마감월 뷰 변경 금지" 규약, ③ 해당 Phase 골든 케이스.
