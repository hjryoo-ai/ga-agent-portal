## 0. 설계의 대전제

1. **돈은 엔진이 계산하고, 포털은 보여준다.** 포털은 어떤 수수료·환수·세액도 스스로 산출하지 않는다. 허용되는 연산은 엔진이 확정한 정수(원) 금액의 **합산과 비율 표시**뿐이다. 세후 실수령액·시뮬레이션 결과는 반드시 엔진에서 받아온다.
2. **상태를 섞지 않는다.** 설계사 신뢰의 핵심은 숫자 자체가 아니라 그 숫자가 **예상(잠정)인지, 확정(마감)인지, 지급완료인지**를 화면이 절대 흐리지 않는 것이다. 모든 금액 옆에는 상태가 붙는다.
3. **읽기 모델은 언제든 처음부터 다시 만들 수 있어야 한다.** 포털 DB는 엔진 이벤트 스트림의 파생물이다. 이벤트 seq 0부터 replay하면 동일한 화면이 재현된다(결정론). 이것이 장애·정정·의심 상황의 유일한 복구 수단이다.
4. **테넌트 격리는 구조로 강제한다.** 본 솔루션은 여러 GA(보험사 자회사형 GA 등)에 공급된다. `tenant_id` 조건이 없는 데이터 접근은 테스트·기동 단계에서 실패해야 하며, DB 수준(RLS)에서 한 번 더 막는다.
5. **설계사 화면에는 설계사 자신의 것만, 필요한 만큼만.** 타인의 수수료·사규 요율표·고객 식별정보는 화면에 나오지 않는다. 시뮬레이션은 설계사 내부 참고용이며 고객 제시 자료가 아니다(§2.3).

## 1. 문제 정의와 사용자

### 1.1 왜 지금 이 화면이 필요한가

| 환경 변화 | 설계사에게 생긴 질문 | 현재 답을 얻는 방법 |
|---|---|---|
| 2026-07-01 1200%룰이 GA→설계사 개인별 지급에 확대 적용(시책·정착지원금 합산) | "이 계약으로 앞으로 시책을 더 받을 수 있나, 한도가 얼마 남았나" | 정산팀에 문의, 또는 모름 |
| 2027-01 분급제 시행 예정(초년도 수수료를 수년에 걸쳐 분할 지급, 감독규정 확정 고시 확인 필요) | "내년부터 매달 실제로 얼마가 들어오나" | 엑셀로 스스로 추정 |
| 환수(해약·실효·철회)의 상계 | "이 계약이 해약되면 이번 달 지급에서 얼마가 빠지나" | 지급명세 받고 나서야 앎 |
| 대형 GA 13개월 정착률 57.8%(2024년 말 기준, 보도), 설계사 이동 증가 | "지금 GA에 남는 게 나은가" — 수입 예측 불가가 이탈을 부추김 | 없음 |

정산 시스템(엔진)은 이 정보를 **전부 이미 가지고 있다**(한도 원장, 분급 스케줄, 환수 채권, 마감 명세). 문제는 설계사가 볼 수 없다는 것뿐이다. 따라서 본 시스템의 본질은 "새 계산"이 아니라 **엔진 원장의 설계사 관점 투영(projection)** 이다.

### 1.2 사용자와 권한 범위

| 사용자 | v1 범위 | 볼 수 있는 것 |
|---|---|---|
| 설계사(본인) | **핵심** | 본인 수수료·한도·분급·환수·명세·알림·시뮬레이션 |
| 조직장(팀장/지점장/본부장) | v2 | 본인 것 + 하위 조직 합계 + 본인 오버라이드 라인. 개별 팀원 라인은 사규 파라미터 |
| 정산 담당자 | v2(지원 콘솔) | 이의제기 응대, 대사 결과, 인제스트 상태, 재구축 실행 |
| 시스템 운영자 | v1(CLI/관리 API) | 테넌트 등록, 인제스트 커서, 재구축 |

### 1.3 설계사의 다섯 가지 질문 (Jobs-to-be-done) → 화면

| # | 질문 | 화면 | 데이터 출처 |
|---|---|---|---|
| Q1 | 이번 달 얼마 들어오나 (세전/세후, 언제) | 홈 | `earnings_month` + 엔진 명세 스냅샷 |
| Q2 | 이 계약 한도가 얼마 남았나, 왜 깎였나 | 한도 현황 | `policy_limit` + 이력 |
| Q3 | 앞으로 매달 얼마 나오나 | 분급 타임라인 | `deferral_item` |
| Q4 | 이 계약이 해약되면 얼마 물어내나 | 시뮬레이션(해약 영향) | 엔진 동기 API |
| Q5 | 이 계약을 체결하면 얼마 받나 | 시뮬레이션(신계약) | 엔진 동기 API |

### 1.4 비즈니스 모델이 설계에 미치는 영향

본 솔루션은 자체 구축 GA 운영 IT 솔루션의 일부로 **보험사 자회사형 GA 등 여러 GA에 공급**된다. 따라서:

- 포털은 **멀티테넌트**다. 한 배포로 여러 GA를 서비스하되 데이터는 완전 격리한다.
- 수수료 엔진은 **교체 가능한 공급원**이어야 한다. 우리 엔진이 기준 구현이지만, 자체 정산 시스템을 보유한 GA는 어댑터로 같은 이벤트 계약(§4)을 맞추면 포털을 그대로 쓸 수 있다. 이것이 포털과 엔진을 **계약(Contract)으로만** 결합하는 이유다.
- 도입 GA의 기존 설계사 앱 안에 **웹뷰로 임베드**될 가능성이 높으므로 모바일 우선 웹으로 만든다.

## 2. 범위

### 2.1 v1 포함

- 화면 5종(§8): 홈, 한도 현황, 분급 타임라인, 시뮬레이션(신계약/해약 영향), 월별 명세(라인 드릴다운)
- 알림함(인앱) + 알림 규칙(§6.5), 이의제기(경량: 라인 단위 문의 접수·상태)
- 엔진 통합 계약 v1(아웃박스 이벤트 피드 + 동기 API 4종) 및 엔진 측 변경(§4.4)
- 멀티테넌시·인증·인가·감사로그, 일일 대사(Recon)·재구축(Rebuild), 데모 테넌트 데이터 생성기

### 2.2 v1 제외 (후속)

조직장 뷰, PDF 지급명세서, 푸시/알림톡 채널, 오프라인 스냅샷 캐시, 계속(유지)수수료 전망(엔진에 스케줄이 없어 룰 없이는 추정 불가), 보험상품 비교·설명 확인서(별도 2순위 기능), 정산 담당자 콘솔 UI.

### 2.3 컴플라이언스 경계 (설계 제약)

- 시뮬레이션 결과는 **설계사 내부 참고용**이다. 화면에 "비확정·고객 제시 불가" 문구를 고정하고, 모든 시뮬레이션 요청·응답을 `simulation_log`에 남긴다(룰 스냅샷 ID 포함, 재현 가능).
- 대형 GA의 비교·설명 의무(동종·유사 3개 이상 비교, 판매수수료 등급·순위 설명)는 고객 대상 절차이며 본 시스템 범위 밖이다. 본 시스템은 설계사가 **자기 한도·수수료를 정확히 알게 함으로써** 변칙 지급 요구나 한도 초과 시도를 사전에 줄이는 방향으로 기여한다.
- 설계사가 보는 요율 정보는 **자기 계산 라인의 근거(적용 요율·지급률·회차)의 실제 수치** 로 한정한다(확정, §14.0). 사규 요율표 전체, 타인 등급·지급률, 다른 상품의 요율은 노출하지 않는다 — 라인 근거는 "이 라인이 왜 이 금액인가"에 답하는 범위까지다.

## 3. 시스템 아키텍처

### 3.1 아키텍처 결정 (Decision Record)

| ID | 결정 | 근거 | 기각한 대안 |
|---|---|---|---|
| D-1 | **별도 저장소·별도 배포** (`ga-agent-portal`). 엔진과는 §4 계약으로만 결합 | 사용자(설계사 vs 정산팀), 노출면(외부 모바일 vs 내부), 배포 주기, 보안 등급이 전부 다르다. 엔진 저장소 내부의 "정본 문서=코드 동일 커밋" 원칙은 각 저장소 안에서 그대로 유지 | 엔진 `commission-api`에 설계사 화면 추가 — 외부 노출면이 돈 원장과 같은 프로세스에 생김 |
| D-2 | **엔진은 테넌트별 인스턴스(물리 분리), 포털은 멀티테넌트(논리 분리 + RLS)** | 돈 원장은 GA별로 분리 배포하는 것이 고객(GA)의 감사·격리 요구에 부합하고 엔진 코드 변경이 없다. 포털은 읽기 전용이라 논리 분리로 충분하며 운영 단가가 낮다 | 엔진 멀티테넌트화 — 원장·락·마감 전부에 tenant 축이 추가되는 대수술 |
| D-3 | **CQRS 읽기 모델 + 아웃박스 pull 피드** (브로커 없음) | 설계사 조회 패턴(설계사×월 키 조회, 마감 익일 오전 집중)은 엔진의 계산 원장 스키마와 맞지 않는다. 엔진 장애와 무관하게 조회가 가능해야 한다. 브로커 없이 커서 기반 pull이면 포트폴리오 실행이 단순하고, Kafka 등으로의 교체는 인제스트 어댑터 한 개 교체로 끝난다 | 화면마다 엔진 동기 조회 — 엔진 가용성에 종속, 집중 시간대 부하 전가 |
| D-4 | **세후 잠정치·시뮬레이션은 엔진의 dry-run API로** | 원천세·상계 순서·환수율은 엔진 룰이다. 포털이 흉내 내는 순간 두 숫자가 어긋난다(대전제 1) | 포털에서 3.3% 곱하기 — 세율·상계 규약이 파라미터라 언젠가 틀린다 |
| D-5 | **포털 DB는 PostgreSQL** (엔진은 Oracle 유지) | 행 수준 보안(RLS)으로 테넌트 격리를 DB가 2차 방어, JSONB로 라인 근거 저장. 읽기 모델은 엔진 DB와 무관하므로 선택 자유 | Oracle 통일 — 고객사 표준이 Oracle이면 어댑터 교체로 대응 가능(도메인·프로젝터는 DB 무의존) |
| D-6 | **모바일 우선 웹(PWA)**, 네이티브 앱 없음 | 도입 GA의 기존 앱에 웹뷰 임베드가 현실적 배포 경로. 한 코드베이스 | 네이티브 — 포트폴리오 범위 초과 |

### 3.2 컴포넌트 구성

```
[ga-commission-engine  (테넌트별 인스턴스, Oracle)]
   │  OUTBOX_EVENT (계산·원장·분급·환수·마감·지급 훅에서 같은 트랜잭션으로 적재)
   │
   ├─ GET  /internal/v1/events?afterSeq=…            ──┐ (pull, 커서)
   ├─ POST /internal/v1/simulations/new-contract     ──┤ (동기)
   ├─ POST /internal/v1/simulations/policy-event     ──┤
   └─ GET  /internal/v1/agents/{id}/statements/{ym}  ──┘ (대사·잠정 명세)
                                                       │
[ga-agent-portal (멀티테넌트, PostgreSQL)]             │
   portal-ingest   ─ 테넌트별 poller → 멱등 적용 → 프로젝터 → 알림 파생
   portal-query    ─ /api/v1/me/**  (설계사 self 조회, agent_id는 토큰에서만)
   portal-sim      ─ 엔진 동기 호출 프록시 + simulation_log
   portal-recon    ─ 일일 대사, DRIFT 처리, 재구축 명령
   web/            ─ React PWA (홈·한도·분급·시뮬·명세·알림)
   ▲
   │ OIDC (테넌트별 IdP / 개발용 Keycloak)
[설계사 스마트폰·태블릿 / GA 기존 앱 웹뷰]
```

### 3.3 모듈 구성 (Gradle 멀티모듈 + pnpm)

```
ga-agent-portal/
├── contracts/                # 엔진↔포털 계약: JSON Schema (events/v1/*.json, api/v1/openapi.yaml)
├── portal-domain             # 포털 고유 값객체(CalcId, PolicyNo, LedgerId, ScheduleId, CommType), 뷰 모델, 상태 열거형. platform-core만 의존
├── portal-projection         # 프로젝터(이벤트→뷰 변환) 순수 로직 + 알림 파생 규칙. DB 무의존
├── portal-ingest             # 이벤트 피드 클라이언트, 커서, 멱등 적용, 실패 격리, 재구축 실행기
├── portal-query              # 조회 서비스·REST 컨트롤러, 인가 정책
├── portal-sim                # 엔진 시뮬레이션·명세 dry-run 프록시, simulation_log
├── portal-recon              # 대사 배치, DRIFT 상태 전이, 관측 지표
├── portal-infra              # PostgreSQL 어댑터(platform-spring `TenantScopedRepository` 하위 저장소), RLS 세션 바인딩, Flyway
├── portal-app                # Spring Boot 조립, 보안 설정, 스케줄러
├── portal-demo               # 데모 테넌트 데이터 생성기(§부록 B), 로컬 엔진 대체용 이벤트 재생기
└── web/                      # React 19 + TypeScript + Vite (PWA)
```

의존 방향: `app → query/ingest/sim/recon → projection → domain`. `infra`는 어댑터로서 `app`에서만 조립된다. `projection`은 DB·Spring 무의존이어야 하며(인메모리 저장소로 밀리초 단위 테스트), 이는 엔진의 `commission-calc` 원칙과 동일하다.

**플랫폼 아티팩트(v1.2)**: 공용 값객체 `Won`·`Ratio`·`Ym`·`TenantId`·`AgentId`와 `TenantContext`는 ga-disclosure가 발행하는 `com.ga.platform:platform-core` 0.2.0의 것을 쓴다(§11 플랫폼 행). 포털은 같은 단순 이름의 클래스를 만들지 않고(아키텍처 테스트), 플랫폼 API가 모자라면 포털에서 보충하지 않고 ga-disclosure 쪽 정비로 올린다. `portal-domain`·`portal-projection`이 의존할 수 있는 외부 모듈은 `platform-core`뿐이고, `platform-spring`(세션 바인딩·저장소 기반 클래스)은 `infra`·`app`에서만 쓴다.

### 3.4 데이터 흐름 3종

1. **투영 경로(비동기)**: 엔진 트랜잭션 커밋 → OUTBOX 적재 → 포털 poller(테넌트별, 주기 5~30초) → `ingest_event` 멱등 검사 → 프로젝터 적용 + 알림 파생(같은 트랜잭션) → 커서 전진. 화면은 `asOf(seq, at)`를 항상 함께 표시한다.
2. **동기 경로**: 시뮬레이션·잠정 명세 갱신 요청 → `portal-sim` → 엔진 API(서비스 토큰) → 결과 로그 → 응답. 엔진 불가 시 화면은 "잠시 후 다시" + 마지막 스냅샷 시각을 보여주고 **투영 경로 데이터는 그대로 서비스**한다.
3. **대사 경로(배치)**: 매일 새벽 테넌트별로 당월(ESTIMATE)·직전 마감월(CONFIRMED) 명세를 엔진에서 받아 포털 합산과 비교 → 불일치 시 해당 설계사×월을 `DRIFT`로 표시하고 화면에 "확인 중" 배지 → 자동 재구축 시도 → 지속 시 운영 알림.

## 4. 엔진↔포털 통합 계약 (Integration Contract v1)

계약은 `contracts/` 폴더에 JSON Schema·OpenAPI로 둔다. 엔진 저장소는 같은 스키마로 **발행 이벤트를 검증하는 provider 테스트**를 가진다(§13). 스키마 변경은 `version` 필드 증가와 호환성 규칙(§4.5)을 따른다.

### 4.1 이벤트 피드

**엔진 측 테이블**

```sql
CREATE TABLE OUTBOX_EVENT (
  seq          NUMBER PRIMARY KEY,           -- 인스턴스(=테넌트) 내 단조 증가 (시퀀스)
  event_id     VARCHAR2(36) NOT NULL UNIQUE, -- UUID, 멱등키
  event_type   VARCHAR2(40) NOT NULL,
  schema_ver   NUMBER(3) NOT NULL,
  aggregate_kind VARCHAR2(30), aggregate_id VARCHAR2(40),
  occurred_at  TIMESTAMP NOT NULL,
  payload      CLOB NOT NULL,                -- JSON
  created_at   TIMESTAMP DEFAULT SYSTIMESTAMP
);
```

- 적재는 **업무 트랜잭션과 동일 트랜잭션**에서 일어난다. `COMM_CALC` 저장 후 훅(`CalcResultListener` 체인)에 `OutboxPublisher`를 추가하는 것이 핵심 변경이며, 분급 상태 전이·환수 채권·마감·지급 런에도 같은 방식의 훅을 둔다.
- 보존: append-only, 삭제 금지. 용량 대비 원장 대비 작다. 보존 기간 축소가 필요해지면 `TenantSnapshot` 이벤트(전체 뷰 상태 덤프)를 주기 발행하고 그 이후만 보존한다(§14 미결정).

**피드 API**

```
GET /internal/v1/events?afterSeq={n}&limit={≤1000}
→ { "events": [Envelope...], "nextSeq": n', "headSeq": h, "schemaVersion": 1 }
```

- 응답 순서는 `seq` 오름차순, 갭 없음. `headSeq − nextSeq`가 포털의 지연 지표.
- 인증: 서비스 토큰(운영은 mTLS 권장). 설계사 토큰으로는 절대 접근 불가.

**Envelope**

```json
{
  "eventId": "6f1c…", "seq": 10231, "type": "CommissionCalculated", "version": 1,
  "occurredAt": "2026-09-22T10:15:30+09:00",
  "aggregate": { "kind": "COMM_CALC", "id": "884213" },
  "payload": { ... }
}
```

### 4.2 이벤트 카탈로그

| 타입 | 발생 시점(엔진) | 핵심 payload | 포털 프로젝터 효과 |
|---|---|---|---|
| `AgentSnapshot` | 설계사 마스터·소속·등급 변경 시, 재구축 부트스트랩 시 | agentId, nameMasked?, name, grade, orgPath, role, status, validFrom | `agent_profile` upsert |
| `CommissionCalculated` | `COMM_CALC` 저장 후 훅 | calcId, agentId, policyNo, productKey, commType, amount(정수 원, 환수·취소는 음수), closeYm, reversalOfCalcId?, limitCutAmt, limitCutPolicy(CUT/DEFER_AFTER_FY)?, basis{rate, payoutRate, installmentNo, ruleVersionIds[]}, policySummary{contractDate, monthlyPremium, productName, insuredMasked} | `earnings_line` upsert, `earnings_month` 합산 갱신, 알림(한도 삭감·환수) |
| `AdjustmentPosted` | 마감 후 정정 등록 | adjId, targetCalcId, agentId, amount, closeYm(익월), reason | `earnings_line`(commType=ADJUSTMENT) |
| `LimitLedgerOpened` | 한도 원장 개설 | ledgerId, policyNo, agentId, contractDate, fyStart, fyEnd, monthlyPremium, limitMultiple, limitAmount, ruleVersionId | `policy_limit` insert |
| `LimitLedgerPosted` | `LimitLedgerPoster` 전기 | ledgerId, postingSeq, calcId, amount, accumAfter | `policy_limit.accum_paid = accumAfter`, 이력 append, 임계치 알림 |
| `LimitLedgerRebased` | 보험료 변경으로 한도 재산정 | ledgerId, postingSeq, oldLimit, newLimit, monthlyPremium, reason | 한도액 갱신, 이력 append, 알림 |
| `DeferralScheduled` | `DeferralSplitStep` 확정 후 훅 | scheduleId, sourceCalcId, agentId, policyNo, dueYm, amount, payCondition, curveVersionId, reason(CURVE/LIMIT_DEFER) | `deferral_item` insert |
| `DeferralStatusChanged` | 도래 배치·해약 이벤트 | scheduleId, from, to(RELEASED/HELD/CANCELLED), reason | 상태 갱신, 알림(HELD/CANCELLED) |
| `ClawbackReceivableUpdated` | 채권 생성·상계 | receivableId, agentId, originCalcId, amount, remaining, status | `clawback_item` upsert |
| `PolicyEventObserved` | INBOUND 정규화 후 | policyNo, agentId, eventType(CANCEL/LAPSE/WITHDRAW/REDUCE/REINSTATE/PAYMENT_OVERDUE), occurredOn | `policy_flag` 갱신, 알림 |
| `StatementEstimated` | 야간 배치(지급 로직 dry-run) | agentId, closeYm, gross, clawbackOffset, adjustment, withholdingTax, net, basisSeq, asOf | `earnings_month` 세액·순액(예상) 갱신, status=ESTIMATED |
| `StatementConfirmed` | 월마감 확정 | agentId, closeYm, gross, clawbackOffset, adjustment, withholdingTax, net, closedAt | status=CONFIRMED (이후 해당 월 라인 변경 금지) |
| `PayoutCompleted` | 지급 런 완료 | agentId, closeYm, paidAt, paidAmount | status=PAID, 알림 |

환수는 별도 타입이 아니다. 엔진에서 환수는 음수 `COMM_CALC`이므로 `CommissionCalculated(commType=CLAWBACK, amount<0)`로 들어오고, 채권화 여부만 `ClawbackReceivableUpdated`가 보강한다.

### 4.3 동기 API (엔진 제공)

| API | 요청 | 응답 | 용도 |
|---|---|---|---|
| `POST /internal/v1/simulations/new-contract` | agentId, productKey, monthlyPremium, contractDate, paymentTermMonths?, incentiveCodes[]? | limitAmount, fyCommissionByInstallment[{no, amount}], incentives[{code, amount, limitIncluded}], projectedAccum, deferral{firstYearPayout, schedule[{dueYm, amount}]}, ruleSnapshotId, generatedAt | Q5 |

시뮬레이션은 엔진 파이프라인을 **영속화 없이(dry-run)** 실행한다. 한도 원장 락을 잡지 않으며 원장 상태는 읽기만 한다(엔진 설계서 §6.1의 게이트 판정을 read-only 모드로 호출).

### 4.4 엔진 저장소 변경 목록 (ga-commission-engine, 별도 PR)

1. `OUTBOX_EVENT` DDL(Flyway) + `OutboxPublisher implements CalcResultListener` — 저장 후 훅 체인에 등록.
2. 분급 상태 전이(`commission-deferral`), 채권 갱신(`commission-clawback`), 마감·지급(`commission-settlement`), 한도 원장 개설·재산정(`commission-limit`)에 동일 훅 적용.
3. `StatementEstimated` 배치(`commission-batch`): 지급 런 로직을 dry-run 모드로 실행해 설계사별 잠정 명세 발행. 주기는 배치 파라미터(**기본 야간 1회**, 확정 §14.0). 이벤트 후 지연 재산출·온디맨드 갱신은 같은 dry-run 서비스를 다른 트리거로 호출하는 것이므로 주기 변경에 코드 수정이 없어야 한다.
4. `commission-api`: 이벤트 피드, 시뮬레이션 2종, 명세 조회 컨트롤러(기존 로드맵 Phase 9 잔여 흡수).
5. `contracts/events/v1` 스키마에 대한 provider 검증 테스트(골든 시나리오 실행 → 발행 이벤트 시퀀스가 스냅샷과 일치).
6. 마감 이후 해당 `closeYm`의 `CommissionCalculated` 발행 금지 불변식 테스트(이미 마감 불변성 테스트가 있으므로 이벤트 측면만 추가).

### 4.5 계약 버전·호환성 규칙

- 필드 **추가**는 호환(포털은 모르는 필드 무시). 필드 **삭제·의미 변경·타입 변경**은 `version` 증가 + 포털 프로젝터의 버전 분기.
- 포털은 자신이 지원하는 최대 version보다 큰 이벤트를 만나면 **그 테넌트 인제스트를 정지**하고 운영 알림(잘못 해석한 숫자를 보여주는 것보다 멈추는 것이 낫다).
- `seq` 갭·역순·중복은 각각 정지·무시·무시(§6.1).

## 5. 읽기 모델 (포털 스키마, PostgreSQL)

모든 테이블은 `tenant_id`를 첫 컬럼으로 갖고 PK·UNIQUE·인덱스에 포함한다. 금액은 `BIGINT`(정수 원). 이하 핵심 테이블만 기술하며 DDL은 Flyway로 관리한다.

```sql
CREATE TABLE tenant (
  tenant_id        TEXT PRIMARY KEY,
  name             TEXT NOT NULL,
  engine_base_url  TEXT NOT NULL,                -- D-2: 테넌트별 엔진 인스턴스

  limit_crit_pct   NUMERIC(5,2) NOT NULL DEFAULT 95,   -- 예시값
  payout_day_rule  TEXT NOT NULL,                -- 예: "NEXT_MONTH_D10" (지급예정일 표시용)
  params           JSONB NOT NULL DEFAULT '{}'   -- 사규 파라미터. 확정된 키(§14.0):
                                                 --   org_member_lines_visible : bool, 기본 false (조직장 뷰의 개별 팀원 라인 노출)
                                                 --   forecast_scenario_enabled: bool, 기본 false (분급 타임라인 유지율 가정 토글)

);

  PRIMARY KEY (tenant_id, subject)
);

CREATE TABLE agent_profile (
  tenant_id TEXT, agent_id TEXT, name TEXT NOT NULL, grade TEXT, org_path TEXT NOT NULL, -- 예: /HQ1/BR03/TM07

  PRIMARY KEY (tenant_id, agent_id)
);

CREATE TABLE earnings_line (
  tenant_id TEXT, calc_id TEXT, agent_id TEXT NOT NULL, policy_no TEXT NOT NULL,

);
```

**RLS**: 모든 테넌트 테이블에 `ENABLE ROW LEVEL SECURITY` + `POLICY tenant_isolation USING (tenant_id = current_setting('app.tenant_id'))`. 애플리케이션은 트랜잭션마다 `SET LOCAL app.tenant_id`를 설정하고(데이터소스 인터셉터), 설정이 없으면 어떤 행도 보이지 않는다. 앱 계정은 RLS를 우회할 수 없는 일반 롤이다.

**불변식(테스트로 상시 검증)**
- `earnings_month.gross/clawback_offset/adjustment = Σ earnings_line` (테넌트·설계사·월 단위).
- `policy_limit.accum_paid ≤ limit_amount`, `policy_limit_history`의 `accum_after − 직전 accum_after = amount`(불일치 시 이벤트 적용 실패 → 인제스트 정지, 엔진 이상 신호).
- `status`가 CONFIRMED/PAID인 월의 라인은 이후 이벤트로 변경되지 않는다(변경 시도 → 인제스트 정지 + 운영 알림).

## 6. 핵심 로직

### 6.1 인제스트 규약

- 테넌트별 단일 워커(순서 보장). 배치 단위로 pull → 이벤트마다 **하나의 DB 트랜잭션**: `ingest_event` insert(중복이면 SKIPPED로 종료) → 프로젝터 적용 → 알림 파생 → `ingest_cursor` 갱신. 트랜잭션 실패 시 롤백되고 커서는 전진하지 않는다.
- `seq` 규칙: 기대값(`last_seq+1`)보다 작으면 무시, 같으면 적용, 크면(갭) 정지·FAILED. 정지된 테넌트는 화면에 "데이터 동기화 지연" 배너를 띄운다(마지막 동기 시각 표시).
- 독 이벤트(스키마 위반·불변식 위반)는 **해당 테넌트만** 정지시킨다. 다른 테넌트 인제스트는 영향 없음(격리 테스트).
- 재처리 명령(`ingest resume --tenant X --from-seq n`)은 운영자 전용, `audit_access`에 기록.

### 6.2 상태 매핑 (엔진 → 화면)

| 엔진 사실 | `earnings_month.status` | 화면 라벨 | 세후 표시 |
|---|---|---|---|
| 라인만 존재 | PROVISIONAL | **예상** | "세후는 야간 산출 후 표시" |
| `StatementEstimated` 수신 | ESTIMATED | **예상** (기준 시각 표시) | 예상 원천세·예상 실수령 |
| `StatementConfirmed` 수신 | CONFIRMED | **확정** | 확정 원천세·확정 실수령 |
| `PayoutCompleted` 수신 | PAID | **지급완료** (지급일) | 지급액 |

| 분급 상태 | 화면 라벨 |
|---|---|
| SCHEDULED | 예정 |
| RELEASED | 이번 달 지급 대상 |
| HELD | 보류 — 사유 표시(예: 해당월 유지 조건 미충족) |
| CANCELLED | 취소 — 사유 표시(해약·실효 등) |

라인의 `reversal_of_calc_id`가 있으면 원본 라인은 "취소됨"으로 접히고 음수 라인과 짝지어 표시한다. 합산에는 둘 다 포함된다(엔진과 동일 규약).

### 6.3 한도 뷰 규칙

- `remaining = limit_amount − accum_paid`, `utilization = accum_paid / limit_amount`(표시용 소수 1자리, 저장하지 않음).
- 경고 단계: `utilization ≥ limit_warn_pct` → WARN, `≥ limit_crit_pct` → CRITICAL, `remaining = 0` → FULL. 임계치는 테넌트 파라미터.
- 삭감/이연: `earnings_line.limit_cut_amt > 0`인 라인을 계약별로 합산해 `cut_total`(CUT)·`deferred_total`(DEFER_AFTER_FY)로 표시하고, 이연분은 `deferral_item(reason=LIMIT_DEFER)`와 연결한다.
- 2026-07-01 이전 체결 계약은 엔진이 원장을 열지 않으므로 화면에 "한도 미적용 계약(체결일 기준)"으로 표시한다. 이 분기는 포털이 판단하지 않는다 — 원장 이벤트가 없다는 사실로만 표시한다.
- `fy_end`까지 남은 일수, 재산정(REBASE) 이력, 계약 상태 배지(`policy_flag`)를 함께 보여준다.

### 6.4 분급 전망 규칙 (포털이 하는 유일한 "계산"의 경계)

- 기본 전망 = 월별 `Σ deferral_item.amount where status ∈ {SCHEDULED, RELEASED}`. HELD는 별도 색으로 표시, CANCELLED는 제외.
- **시나리오 토글**: "전건 유지"(기본) / "유지율 가정 p%" — 월별 합계에 p를 곱해 표시. 기능은 v1에 구현하되 **테넌트 파라미터 `forecast_scenario_enabled`가 기본 false**이므로(확정, §14.0) 화면에서 토글이 노출되지 않고 API도 `scenario=RETENTION` 요청을 400으로 거부한다. 활성화한 테넌트에서는 "비확정·참고" 문구가 고정된다. 구현은 `ForecastScenario` 한 클래스에 격리하고, 이 클래스 외부에서 금액에 비율을 곱하는 코드는 아키텍처 테스트로 금지한다.
- 계속(유지)수수료는 엔진에 스케줄이 없으므로 전망에 포함하지 않는다. 화면에 "분급 확정 스케줄만 반영" 문구를 둔다.
- 2027 분급제의 상품군별 적용 여부(일부 상품 제외 가능성 보도)는 엔진 커브 데이터가 결정한다. 포털은 `deferral_item`이 있으면 보여주고 없으면 보여주지 않을 뿐이다.

### 6.5 알림 규칙

알림은 프로젝터 적용과 **같은 트랜잭션**에서 파생되며 `dedup_key`로 중복을 막는다.

| 트리거 이벤트 | 조건 | dedup_key | 심각도 |
|---|---|---|---|
| `LimitLedgerPosted` | utilization이 WARN/CRIT/FULL 경계를 **상향 통과** | `LIMIT_{LEVEL}:{ledgerId}` | INFO/WARN/CRIT |
| `CommissionCalculated` | `limitCutAmt > 0` | `LIMIT_CUT:{calcId}` | WARN |
| `LimitLedgerRebased` | 항상 | `LIMIT_REBASE:{ledgerId}:{postingSeq}` | INFO |
| `CommissionCalculated` | commType=CLAWBACK | `CLAWBACK:{calcId}` | WARN |
| `DeferralStatusChanged` | to ∈ {HELD, CANCELLED} | `DEFER_{to}:{scheduleId}` | WARN |
| `PolicyEventObserved` | PAYMENT_OVERDUE/LAPSE/CANCEL | `POLICY_{type}:{policyNo}:{occurredOn}` | WARN |
| `StatementConfirmed` | 항상 | `STMT_CONFIRMED:{ym}` | INFO |
| `PayoutCompleted` | 항상 | `PAYOUT:{ym}` | INFO |
| 이의제기 답변 | status→ANSWERED | `INQUIRY:{inquiryId}` | INFO |

같은 날 같은 타입이 다수 발생하면 하루 1건의 다이제스트로 묶는 옵션(테넌트 파라미터). 채널은 v1 인앱, 이후 푸시·알림톡은 `NotificationChannel` 어댑터 추가.

### 6.6 대사(Recon)와 DRIFT

- 매일 새벽 테넌트별로 활성 설계사 전원에 대해 당월(ESTIMATE)·직전 마감월(CONFIRMED) 명세를 엔진에서 페이지 단위로 조회하고 `earnings_month`의 포털 합산(gross/offset/adjustment)과 비교한다.
- 불일치 → `recon_result=DRIFT`, `earnings_month.data_status=DRIFT`. 화면은 해당 월 카드에 "확인 중" 배지를 붙이고 금액을 **흐리게** 표시한다(틀릴 수 있는 숫자를 확정처럼 보여주지 않는다).
- 자동 복구: 해당 테넌트 재구축(§6.7)을 그림자 스키마에서 수행 → 재대사 → 일치하면 스왑, `REPAIRED`. 여전히 불일치면 운영 알림(엔진 측 정정 가능성).

### 6.7 재구축(Rebuild)

- `rebuild --tenant X`: 그림자 스키마 생성 → `ingest_cursor=REBUILDING` → seq 0부터 replay → 불변식 검증 → 대사 → 스왑 → 정상 인제스트 재개. 재구축 중에도 기존 스키마로 조회는 계속된다.
- 결정론 테스트: 동일 이벤트 스트림을 두 번 replay하면 모든 뷰 테이블이 바이트 단위로 동일하다.

## 7. 조회 API (포털 → 웹)

self 엔드포인트의 경로에는 `agentId`가 **없다**. 설계사 식별은 토큰 subject → `identity_link` 조회로만 이뤄지며, 이는 IDOR를 구조적으로 제거한다.

| 메서드/경로 | 응답 요약 |
|---|---|
| `GET /api/v1/me` | 프로필(마스킹된 이름·등급·소속·역할), 테넌트 표시 파라미터, 동기화 상태(asOf, 지연 여부) |
| `GET /api/v1/me/earnings?from=YYYYMM&to=YYYYMM` | 월별 요약 시계열(gross/offset/adjustment/tax/net/status/data_status) |
| `GET /api/v1/me/earnings/{ym}` | 월 요약 + 유형별 합계 + 지급예정일(테넌트 규칙) |
| `GET /api/v1/me/earnings/{ym}/lines?page&size&commType&policyNo` | 라인 목록(취소 짝 접기) |
| `GET /api/v1/me/earnings/lines/{calcId}` | 라인 상세: 근거(basis), 한도 판정(limitCut), 연결 분급·환수, 문의 버튼 |
| `GET /api/v1/me/limits?status=WARN\|CRIT\|FULL\|ALL` | 계약별 한도 카드 목록 |
| `GET /api/v1/me/limits/{ledgerId}` | 한도 상세 + 이력 타임라인 |
| `GET /api/v1/me/deferrals?from&to&scenario=ALL_INFORCE\|RETENTION&p=` | 월별 전망 + 항목 |
| `POST /api/v1/me/simulations/new-contract` / `/policy-event` | 엔진 결과 + simId(로그 참조) |
| `GET /api/v1/me/notifications?unreadOnly` / `PATCH .../{id}/read` | 알림함 |
| `POST /api/v1/me/inquiries` / `GET /api/v1/me/inquiries` | 이의제기 |
| `GET /api/v1/org/…` | v2. 조직장 하위 조회. `org_path` 접두 일치로 인가, 접근은 `audit_access` 기록 |

모든 응답 공통 필드: `asOf: {seq, at}`, `dataStatus: OK|DRIFT|SYNC_DELAYED`. 금액은 정수 원, 통화 포맷은 프론트 담당.

**응답 예시 — `GET /api/v1/me/earnings/202609`**

```json
{
  "closeYm": "202609", "status": "ESTIMATED", "dataStatus": "OK",
  "gross": 4130000, "clawbackOffset": -350000, "adjustment": 0,
  "withholdingTax": 124740, "net": 3655260,
  "byType": { "FY_COMM": 2800000, "INCENTIVE": 800000, "RENEWAL": 530000, "CLAWBACK": -350000 },
  "estimateAsOf": "2026-09-22T02:10:00+09:00",
  "payoutExpectedOn": "2026-10-10",
  "asOf": { "seq": 10231, "at": "2026-09-22T10:15:41+09:00" }

```
(금액·세율은 예시값. 세액·순액은 엔진 `StatementEstimated`에서 온 값이며 포털은 계산하지 않는다.)

## 8. 화면 설계 (모바일 우선, 텍스트 와이어)

**공통**: 상단에 동기화 상태 칩(`기준 09-22 10:15` / `동기화 지연` / `확인 중`). 모든 금액 옆 상태 라벨(예상·확정·지급완료). 원 단위 정수, 천 단위 구분.

1. **홈**
   - 이번 달 카드: 실수령 예상/확정(큰 숫자) · 세전 · 환수 상계 · 원천세 · 지급예정일 D-n · 상태 라벨
   - 전월 대비(확정 기준) 한 줄
   - 주의 계약: 한도 WARN 이상 N건, 납입 지연/실효 예고 M건 → 한도 현황으로 이동
   - 다음 달 분급 예정액 한 줄 → 타임라인으로 이동
   - 최근 알림 3건
2. **한도 현황**
   - 필터(주의/전체) · 계약 카드: 상품명 · 피보험자(마스킹) · 체결일 · 소진 바(%) · 잔여액 · 초년도 종료 D-n · 계약 상태 배지
   - 상세: 한도액 산식(월납 × 배수, 규정 기준일) · 원장 타임라인(전기·재산정) · 삭감/이연 내역(연결된 분급 항목) · "이 계약 해약 시 영향" 버튼(→ 시뮬레이션)
3. **분급 타임라인**
   - 기간 토글(12/24/48/84개월) · 월별 막대(예정/지급대상/보류 구분) · 시나리오 토글(전건 유지 / 유지율 가정) · 계약 필터
   - 하단 고정 문구: "분급 확정 스케줄만 반영 · 참고치 · 비확정"
4. **시뮬레이션**
   - 탭 ① 신계약 예상: 상품 선택 · 월납보험료 · 계약일(기본 오늘) → 초년도 회차별 예상 · 한도액과 예상 소진 · 시책 포함 여부 · 분급 첫해/이후 스케줄
   - 탭 ② 해약 영향: 계약 선택 · 시점 → 환수액 · 이번 달 실수령 변화(전/후) · 취소되는 분급 항목 · 채권 잔액
   - 고정 문구: "설계사 참고용 · 비확정 · 고객 제시 불가" · 결과에 룰 스냅샷 ID 표기
5. **월별 명세**
   - 월 선택 · 유형별 합계 → 라인 목록(계약·유형·금액·상태·취소 짝) → 라인 상세(적용 요율·지급률·회차, 한도 판정, 연결 항목) → "이 항목 문의하기"
6. **알림함 / 설정**: 읽음 처리, 다이제스트 설정(테넌트 허용 시).

접근성·현장성: 최소 터치 44px, 큰 숫자 우선, 저사양 기기 고려(번들 크기 상한을 CI에서 검사), 화면 캡처 방지는 하지 않는다(설계사 본인 데이터).

## 9. 보안·개인정보·멀티테넌시

- **인증**: OIDC. 테넌트별 IdP(도입 GA의 SSO) 또는 포털 기본 IdP. 개발·데모는 Keycloak. 토큰 클레임: `sub`, `tenant_id`, `roles`. `agent_id`는 클레임에서 신뢰하지 않고 `identity_link`로 해석한다.
- **인가**: self 엔드포인트는 컨텍스트의 `agent_id`로만 조회. 조직 조회(v2)는 `agent_profile.org_path` 접두 일치 + 역할 검사, 전 건 `audit_access` 기록.
- **테넌트 격리 3중**: ① 요청 필터가 `TenantContext` 설정, 없으면 401 ② 저장소 계층은 `TenantScopedRepository`만 허용 — 아키텍처 테스트(ArchUnit + SQL 소스 스캔)로 `tenant_id` 조건 없는 쿼리 금지 ③ PostgreSQL RLS.
- **개인정보 최소화**: 포털은 고객 이름을 마스킹 형태로만 저장(엔진이 마스킹해 발행), 주민번호·연락처·주소는 수신하지 않는다. 증권번호는 저장하되 화면은 뒷자리 일부만 표시. 저장소 암호화(디스크·백업), 전송 TLS.
- **보존**: 알림 1년, 시뮬레이션 로그 3년(예시값, 테넌트 파라미터), 감사로그 5년(예시값). 라인·명세는 엔진 보존 정책에 종속(재구축 가능하므로 포털 자체 보존은 운영 편의 기간으로 축소 가능).
- **서비스 간 인증**: 포털→엔진은 서비스 토큰(운영 mTLS). 엔진 `/internal/**`는 포털 네트워크에서만 접근.
- **레이트 리밋**: 시뮬레이션·온디맨드 명세 갱신은 설계사당 분당 N회(파라미터). 초과 시 마지막 결과 재표시.

## 12. 구현 로드맵 (Claude Code 작업 순서)

각 Phase는 독립 머지 가능해야 하며 완료 기준을 테스트로 증명한다. `E-`는 엔진 저장소 작업.

- **Phase 0 — 골격**: 저장소·Gradle 모듈·Flyway·Testcontainers(PostgreSQL)·`Won`/`Ym`/`TenantId` 값객체·`TenantContext`·RLS 세션 바인딩·아키텍처 테스트·`contracts/` 초기 스키마. *완료 기준: tenant 조건 없는 저장소 메서드가 테스트에서 실패, RLS 미설정 세션에서 0행.*
- **Phase E1 — 엔진 아웃박스**: §4.4 1·2·5·6. *완료 기준: 엔진 골든 시나리오 실행 시 발행 이벤트 시퀀스가 스냅샷 파일과 일치, 스키마 검증 통과.*
- **Phase 1 — 인제스트**: poller·커서·멱등·seq 규칙·독 이벤트 격리·재처리 명령. *완료 기준: 중복/역순/갭/재시작/테넌트 간 격리 테스트 통과.*
- **Phase 2 — 프로젝션**: earnings·limit·deferral·clawback·flag 프로젝터, 불변식, 재구축, 결정론. *완료 기준: 부록 A 시나리오 이벤트 스트림 → 뷰 골든 테스트, replay 2회 동일.*
- **Phase 3 — 조회 API·인증·인가**: `/api/v1/me/**`, `identity_link`, IDOR 테스트(타인 calcId 조회 404), 감사로그. *완료 기준: 인가 매트릭스 테스트 전건 통과.*
- **Phase 4 — 프론트 1차**: 홈·월별 명세·한도 현황·알림함, 동기화 상태 칩, 상태 라벨 규약. *완료 기준: Playwright 시나리오(예상→확정→지급완료 전이 표시).*
- **Phase E2 — 엔진 동기 API**: §4.4 3·4(시뮬레이션 2종 dry-run, 명세 조회, 야간 `StatementEstimated`). *완료 기준: dry-run이 원장·COMM_CALC에 아무 것도 남기지 않음을 테스트.*
- **Phase 5 — 시뮬레이션·분급 타임라인**: `portal-sim`, `simulation_log`, 시나리오 토글(`ForecastScenario` 격리 테스트). *완료 기준: 엔진 응답 스텁으로 계약 테스트, 고정 문구 렌더 테스트.*
- **Phase 6 — 알림 파생·이의제기**: §6.5 규칙, dedup, 다이제스트, inquiry API. *완료 기준: 경계 상향 통과 시 1회만 발생, 하향·재상향 케이스.*
- **Phase 7 — 대사·DRIFT·관측성**: §6.6, 지표·트레이스, 운영 알림. *완료 기준: 인위적 라인 누락 주입 → DRIFT 감지 → 자동 재구축 → REPAIRED.*
- **Phase 8 — 데모 테넌트·통합 실행**: 부록 B 생성기, docker compose, README(포트폴리오 관점), E2E. *완료 기준: `docker compose up` 후 데모 설계사로 로그인해 5개 화면 모두 데이터 표시.*
- **Phase 9 (후속)** — 조직장 뷰, PDF 명세, 푸시/알림톡, 오프라인 스냅샷.

Claude Code에 지시할 때 각 Phase 프롬프트에 반드시 포함할 것: ① 본 설계서 해당 섹션, ② "포털은 금액을 계산하지 않는다(합산·비율 표시만), double 금지, tenant_id 없는 접근 금지, agent_id는 identity_link로만 해석, 마감월 뷰 변경 금지" 규약, ③ 해당 Phase 골든 케이스.

## 부록 C. 포트폴리오 관점 메모

README에서 강조할 것: ① 돈을 다시 계산하지 않고 "보여주기"에 집중한 이유와 그 경계(합산·비율만) ② 예상/확정/지급완료 3상태와 DRIFT "확인 중" — 신뢰를 UI 규약으로 만든 사례 ③ 아웃박스 pull 피드로 브로커 없이 재구축 가능한 읽기 모델 ④ 멀티테넌트 3중 격리(컨텍스트·아키텍처 테스트·RLS) ⑤ 두 저장소 사이의 계약 버전 관리. 엔진 저장소와 동일하게 AI 협업 방법론(설계서 → Phase 지시 → 증거 기반 수용)을 한 섹션으로 기록한다.
