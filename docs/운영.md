# 포털 운영 절차 (ga-agent-portal)

> 포털 Phase 3(조회 API·인증·인가)부터의 운영 등록 절차. 설계서 §9 v1.6이 정본이고 이 문서는 그 절차를 적는다. 값(발급자 URL·subject·설계사 ID·비밀)은
> 이 문서와 저장소 어디에도 쓰지 않는다 — 아래 SQL의 `<…>`는 자리표시다. 등록 SQL은 **파일**로 만들어 `psql -f`로 돌린다(셸 인자·환경 변수에 값을 싣지 않는다).
> 모든 등록·해제는 스키마 소유자 `portal_migrator`로, 그 테넌트를 세션에 설정한 트랜잭션 안에서 한다(`tenant`·`identity_link`는 FORCE RLS).

## 1. 테넌트 로그인 열기 — 발급자 등록

토큰의 `iss`가 테넌트를 정한다(설계서 §9). `oidc_issuer`는 정확 일치(대소문자·꼬리 슬래시 포함)이고 테넌트 사이에 유일하다. 둘 다 NULL이면 그 테넌트에는 로그인이 없다.

```sql
-- register-issuer.sql  (psql -v ON_ERROR_STOP=1 -f register-issuer.sql)
BEGIN;
SELECT set_config('app.tenant_id', '<TENANT_ID>', true);
UPDATE tenant SET oidc_issuer = '<https://idp.example/realms/ga01>', oidc_audience = '<portal-ga01>' WHERE tenant_id = '<TENANT_ID>';
COMMIT;
```

- 발급자 메타데이터(`<issuer>/.well-known/openid-configuration`)의 `issuer`가 이 값과 같아야 한다. JWKS는 그 메타데이터에서 받는다(등록된 발급자만 — 토큰이 고른 URL로는 나가지 않는다).
- 해제(로그인 닫기): 둘 다 NULL로. 다음 요청부터 401(캐시 없음).
- 발급자 표는 전용 롤 `portal_issuer`(이 세 열만)로 요청마다 읽는다 — 그 롤의 자격 증명은 `PORTAL_ISSUER_USER`·`PORTAL_ISSUER_PASSWORD`(비밀 관리자에서).

## 2. 설계사 링크 등록 — `identity_link` (AGENT)

설계사·역할은 이 행에서만 온다(토큰의 `agent_id`·`roles` 클레임은 쓰지 않는다). `org_path`는 포털 인가용 조직(v2 조직 조회의 범위) — 엔진의 `agent_profile.org_path`(표시용)와 출처가 다르고, 달라도 어느 쪽도 고치지 않는다.

```sql
-- link-agent.sql
BEGIN;
SELECT set_config('app.tenant_id', '<TENANT_ID>', true);
INSERT INTO identity_link (tenant_id, subject, agent_id, role, status, org_path, linked_at)
VALUES ('<TENANT_ID>', '<IdP subject>', '<AGENT_ID>', 'AGENT', 'ACTIVE', '</HQ1/BR03/TM07>', now());
COMMIT;
```

- 해제: `UPDATE identity_link SET status = 'REVOKED' WHERE tenant_id = '<TENANT_ID>' AND subject = '<IdP subject>';` — 행은 지우지 않는다(감사가 그 주체를 가리킨다). 다음 요청부터 404.
- `MANAGER`는 v2 조직 조회의 역할 — 지금 `/api/v1/me/**`는 `AGENT`만 열린다(`docs/authz-matrix.md`).

## 3. 운영자 등록 — CLI 인가 (OPERATOR)

운영 명령(`ingest status|resume|pause|rebuild`)의 행위자는 **실행한 OS 사용자**다 — subject `cli:<OS 사용자>`가 그 테넌트의 `OPERATOR`·`ACTIVE` 링크여야 한다(`--actor`는 없어졌다 — 쓰면 종료 코드 64). 운영자는 설계사가 아니므로 `agent_id`·`org_path`가 없다.

```sql
-- register-operator.sql
BEGIN;
SELECT set_config('app.tenant_id', '<TENANT_ID>', true);
INSERT INTO identity_link (tenant_id, subject, agent_id, role, status, org_path, linked_at)
VALUES ('<TENANT_ID>', 'cli:<os-user>', NULL, 'OPERATOR', 'ACTIVE', NULL, now());
COMMIT;
```

- 테넌트마다 따로 등록한다. 테넌트를 지정하지 않은 `ingest status`는 테넌트마다 확인해 등록되지 않은 테넌트를 `T not authorized`로 보이고, 하나라도 있으면 종료 코드 2.
- 거부는 그 테넌트의 `audit_access`에 `AUTHZ_DENIED`(detail `NO_LINK`·`REVOKED`·`ROLE`, target `cli:ingest <명령>`)로 남는다.
- `OPERATOR` 링크의 토큰으로 `/api`를 부르면 404다(설계사가 없다).
- 해제는 2와 같이 `REVOKED`.

## 4. `policyKey` 비밀 — 배포와 회전

응답의 `policyKey` = HMAC-SHA256(배포 비밀, `tenant_id` + `U+001F` + `policy_no`) 앞 16자(설계서 §7). 비밀은 파일 `portal.query.policy-key-secret-file`(환경 `PORTAL_POLICY_KEY_SECRET_FILE`, 기본 `/run/secrets/portal-policy-key`) — 32바이트 이상의 무작위 바이트, 소유자만 읽게. 웹 애플리케이션은 이 파일이 없으면 뜨지 않는다.

- **회전하면 모든 `policyKey`가 바뀐다.** 화면(Phase 4)은 키를 저장하지 않는다 — 북마크·저장된 필터의 키는 회전 뒤 빈 결과가 된다(오류가 아니다).
- 회전 절차: 새 비밀 파일 배치 → 인스턴스 순차 재시작(재시작 사이에는 인스턴스마다 키가 다를 수 있다 — 같은 화면이 두 인스턴스를 오가면 필터가 빈 결과일 수 있다).
- 비밀 값은 저장소·로그·티켓에 쓰지 않는다.

## 5. 동기화 지연 기준

`dataStatus = SYNC_DELAYED`의 기준 초는 테넌트 `params.sync_delay_seconds`(1~9자리 양의 정수), 없거나 형식이 틀리면 설정 `portal.query.default-sync-delay-seconds`(기본 300). 커서가 `RUNNING`이 아니면(재구축 중 포함) 기준과 무관하게 지연이다.

```sql
-- sync-delay.sql
BEGIN;
SELECT set_config('app.tenant_id', '<TENANT_ID>', true);
UPDATE tenant SET params = params || '{"sync_delay_seconds": 600}'::jsonb WHERE tenant_id = '<TENANT_ID>';
COMMIT;
```

## 6. 시뮬레이션 — 레이트 리밋·유지율 시나리오·로그 보존·엔진 타임아웃 (포털 Phase 5)

설계서 §9·§10 v1.8. 테넌트 값은 `tenant.params`, 엔진 타임아웃은 앱 설정이다(계획 Q10).

| 키 | 자리 | 기본 | 뜻 |
|---|---|---|---|
| `sim_rate_per_minute` | `tenant.params`(1~9자리 양의 정수) | 앱 설정 `portal.sim.default-rate-per-minute` = 10 | 설계사당 직전 60초 시뮬레이션 요청 수 상한 — 넘으면 429 `RATE_LIMITED` + `Retry-After` |
| `forecast_scenario_enabled` | `tenant.params`(JSON 불리언) | false | 분급 타임라인의 유지율 가정(RETENTION)을 연다 — 꺼져 있으면 `scenario=RETENTION`은 400, 화면에 토글이 없다 |
| `sim_log_retention_years` | `tenant.params`(양의 정수) | 3 | `simulation_log` 보존 연수 — **문서용**: 삭제 잡은 없다(지시문 ②). 아래 SQL을 운영자가 손으로 돌린다 |
| `portal.sim.connect-timeout` · `portal.sim.read-timeout` | 앱 설정(환경 `PORTAL_SIM_CONNECT_TIMEOUT` · `PORTAL_SIM_READ_TIMEOUT`) | 2s · 10s | 엔진 시뮬레이션 호출의 연결·읽기 시간 초과 — 넘으면 503 `ENGINE_UNAVAILABLE`, 재시도 없음 |

```sql
-- sim-params.sql — 리밋 20/분, 유지율 시나리오 켬
BEGIN;
SELECT set_config('app.tenant_id', '<TENANT_ID>', true);
UPDATE tenant SET params = params || '{"sim_rate_per_minute": 20, "forecast_scenario_enabled": true}'::jsonb WHERE tenant_id = '<TENANT_ID>';
COMMIT;
```

보존 정리(테넌트마다, 손으로 — 같은 조건의 `SELECT count(*)`를 먼저 보고 지운다). 재구축은 `simulation_log`를 지우지 않는다(설계서 §6.7):

```sql
-- sim-log-retention.sql
BEGIN;
SELECT set_config('app.tenant_id', '<TENANT_ID>', true);
DELETE FROM simulation_log
 WHERE tenant_id = '<TENANT_ID>'
   AND created_at < now() - make_interval(years => coalesce((SELECT (params->>'sim_log_retention_years')::int FROM tenant WHERE tenant_id = '<TENANT_ID>'), 3));
COMMIT;
```

엔진 서비스 토큰은 인제스트와 같은 파일(`PORTAL_ENGINE_TOKEN_DIR/<TENANT_ID>`)이다 — 파일이 없으면 시뮬레이션은 엔진을 부르지 않고 503(로그 사유 `TOKEN_MISSING`)이고 조회는 그대로다.

## 7. 알림함·이의제기 — 문의 CLI·문의 한도·알림 보존 (포털 Phase 6)

설계서 §6.5·§9·§10 v1.9. 알림은 인제스트 적용 트랜잭션 안에서 생기고(운영자가 할 일 없음), 문의는 설계사가 화면에서 접수하고 운영자가 CLI로 답한다. 푸시·알림톡·메일은 없다(인앱만).

**문의 CLI**(`cli` 프로파일 — 인제스트 명령과 같은 실행기, 같은 인가: `cli:<OS 사용자>`가 그 테넌트의 OPERATOR — §3). 종료 코드 0 성공·2 거부·64 사용법.

| 명령 | 하는 일 | 감사(`audit_access`) |
|---|---|---|
| `inquiry list --tenant=T [--status=OPEN\|ANSWERED\|CLOSED\|ALL]` | 탭 구분 한 줄씩: id·설계사·calcId(없으면 `-`)·분류·상태·접수 시각·**본문**(줄바꿈·탭·역슬래시는 `\n`·`\t`·`\\`로, 그 밖의 제어·서식(양방향 등)·구분 문자는 `\uXXXX`로 — 설계사가 쓴 글이 터미널을 조작하지 못하게). 접수 순 | `INQUIRY_LIST`(target `inquiry:<상태>`) |
| `inquiry answer --tenant=T --id=<uuid> --answer-file=<path>` | `OPEN → ANSWERED`, 답한 이 = `cli:<OS 사용자>`, 같은 트랜잭션에서 설계사에게 알림 `INQUIRY_ANSWERED`. 출력은 `inquiry <id> ANSWERED` 한 줄(답변을 되풀이하지 않는다). `OPEN`이 아니면 2 | `INQUIRY_ANSWER` / `INQUIRY_ANSWER_REJECTED`(target `inquiry:<id>`) |
| `inquiry close --tenant=T --id=<uuid>` | `OPEN`·`ANSWERED → CLOSED`(닫힌 것은 끝 — 다시 열거나 답을 고치지 않는다). 닫힌 것이면 2 | `INQUIRY_CLOSE` / `INQUIRY_CLOSE_REJECTED` |

- **답변은 파일로만.** `--answer` 같은 인자는 없다(64) — 명령행·환경 변수는 셸 기록·프로세스 목록에 남는다. 파일: UTF-8(잘못된 바이트는 거부), 16 KiB 이하, 끝 줄바꿈 하나는 빼고 1~4,000자(코드 포인트), 공백만은 안 된다. 어긋나면 64이고 메시지에 파일 내용은 없다. 다 쓴 파일은 운영자가 지운다(포털은 읽기만).
- 본문이 나오는 곳은 `inquiry list`의 터미널과 작성자 본인의 문의 상세 화면뿐이다. `list` 출력을 파일·티켓·채팅으로 옮기지 않는다. 감사 `detail`·로그·지표에는 본문이 없다.

```sh
# 예: 답변 파일을 쓰고(편집기로 — 셸 인라인 금지), 답하고, 지운다
java -jar portal-app.jar --spring.profiles.active=cli inquiry list --tenant=<TENANT_ID> --status=OPEN
java -jar portal-app.jar --spring.profiles.active=cli inquiry answer --tenant=<TENANT_ID> --id=<INQUIRY_ID> --answer-file=/secure/answers/<INQUIRY_ID>.txt
java -jar portal-app.jar --spring.profiles.active=cli inquiry close --tenant=<TENANT_ID> --id=<INQUIRY_ID>
```

**문의 한도**: 설계사당 직전 24시간 문의 행 수 ≥ N이면 429 `RATE_LIMITED` + `Retry-After`(초). N은 `tenant.params.inquiry_rate_per_day`(1~9자리 양의 정수), 없거나 형식이 다르면 앱 설정 `portal.inbox.default-inquiries-per-day` = 20. 지표 `api_rate_limited_total{tenant, route="inquiries"}`.

```sql
-- inquiry-rate.sql — 문의 한도 10/일
BEGIN;
SELECT set_config('app.tenant_id', '<TENANT_ID>', true);
UPDATE tenant SET params = params || '{"inquiry_rate_per_day": 10}'::jsonb WHERE tenant_id = '<TENANT_ID>';
COMMIT;
```

**알림 보존 1년**(예시값 — 설계서 §9): 삭제 잡은 없다. 읽음 여부와 무관하게 `created_at` 기준으로, 테넌트마다 손으로(같은 조건의 `SELECT count(*)`를 먼저 보고 지운다). 문의(`inquiry`)의 보존 기간은 설계서에 정해져 있지 않다 — 이 Phase에는 문의 정리 SQL이 없다(보고서 다음 Phase 질문).

```sql
-- notification-retention.sql
BEGIN;
SELECT set_config('app.tenant_id', '<TENANT_ID>', true);
DELETE FROM notification WHERE tenant_id = '<TENANT_ID>' AND created_at < now() - interval '1 year';
COMMIT;
```

**재구축과 알림**: 재구축은 알림을 만들지도 지우지도 않는다(`notification`·`inquiry`는 그대로). **재구축 뒤 커서 뒤 이벤트의 알림은 생기지 않는다** — 재구축은 피드 머리까지 재생하므로, `FAILED`에서 재구축하거나 머리가 커서보다 앞서 있으면 그 사이 이벤트는 재구축이 처음 적용하고, 그 사실들의 알림(한도 경고·확정·지급 등)은 없다(계획 Q25). 설계사에게 알려야 할 일이면 운영자가 따로 안내한다. (포털 Phase 7: DRIFT로 막혔던 **달**의 확정·지급 알림만은 재대사 `REPAIRED`가 같은 키로 넣는다 — §8, 설계서 §6.5. 원장·분급·정책 알림은 그대로 없다.)

## 8. 대사·자동 복구·운영 알림 채널 v1 (포털 Phase 7)

설계서 §3.4·§6.6·§6.7·§10 v1.10, 지표·로그·스팬의 닫힌 표는 `docs/지표.md`. 대사는 테넌트마다 하루 한 번 앱 안 스케줄러가 돌린다(KST `recon_hour_kst` 이후 첫 1분 틱 — 그날 스케줄 회차가 없을 때). 운영자는 CLI로 같은 회차를 부를 수 있다. **운영 알림 채널 v1은 지표 + `status` CLI**다 — 이메일·웹훅은 없다(v2).

**CLI**(`cli` 프로파일 — §3의 인가: `cli:<OS 사용자>`가 그 테넌트의 OPERATOR). 출력은 수·상태·시각·나이뿐이다(설계사·달·금액·`calcId` 없음).

| 명령 | 하는 일 | 종료 코드 | 감사 |
|---|---|---|---|
| `recon run --tenant=T [--ym=YYYYMM,…]` | 대사 회차 하나(스케줄러와 같은 진입점). `--ym`이 없으면 창 {당월, 직전 달}(KST), 있으면 그 달들(쉼표, 중복 없이 최대 6). 한 줄: `T recon <결과> checked= matched= drift_new= drift_unresolved= inconclusive= engine_calls= [rebuild=]` | 0 회차 끝(`OK`·`DRIFT`·`REPAIRED`), 1 `FAILED`(자동 재구축 실패), 2 거부·다른 회차 진행 중, 64 사용법 | `RECON_RUN`(target `recon:T`). 자동 재구축은 `INGEST_REBUILD*`(행위자 `recon:T`) |
| `status --tenant=T` · `status --all` | 테넌트마다 한 줄: 커서 상태·`last_seq`·`lag_seq`(엔진 머리 − `last_seq`, 머리를 못 읽으면 `-`)·`caught_up_at`·`lag_s`·`drift_unresolved`·`drift_oldest_days`(가장 오래된 미해결 DRIFT의 나이 — **달은 찍지 않는다**)·`last_run`(시각/결과)·`last_rebuild`·`inquiries_open`·`inquiry_oldest_hours`. `--all`은 테넌트 목록 전체 — 등록되지 않은 테넌트는 `T not authorized` | 0, 하나라도 거부면 2, 64 | `STATUS`(target `cli:status`) 테넌트마다 |

```sh
java -jar portal-app.jar --spring.profiles.active=cli status --all
java -jar portal-app.jar --spring.profiles.active=cli recon run --tenant=<TENANT_ID> --ym=<YYYYMM>
```

**무엇을 보고 무엇을 하나**

| 신호 | 뜻 | 할 일 |
|---|---|---|
| `recon_unresolved_drift{tenant}` > 0 오래(`status`의 `drift_oldest_days` ≥ 1) | 재구축 뒤에도 포털 합 ≠ 엔진 명세 — 시도한 DRIFT는 다시 재구축하지 않는다(스트림 자체의 불일치·엔진 쪽 정정 필요) | 엔진 정산팀에 그 테넌트·달의 정정 여부 확인. 엔진이 정정 이벤트를 내면 이벤트 대사·다음 회차가 푼다. 화면은 그동안 "확인 중" |
| `recon_runs_total{result="FAILED"}` · `status`의 `cursor=FAILED`(`REBUILD_FAILED`) | 자동 재구축 실패 — 커서가 멈췄다 | `ingest status`로 원인(사유 코드·seq) → 원인 수정 → `ingest rebuild --tenant=T`(§6.7) |
| `recon_inconclusive_total{reason="BUDGET"}` 증가 | 회차 예산(`recon_max_calls`·`recon_max_seconds`)이 대상 수보다 작다 | 테넌트 `params`의 상한을 올린다(아래 SQL). 호출 간격 `recon_call_interval_ms`와 엔진 부하를 함께 본다 |
| `recon_inconclusive_total{reason="LAGGING"}` 증가 | 포털이 뒤처진 채 회차가 돌았다(커서 비`RUNNING`·따라잡은 지 오래·엔진 머리가 앞) — DRIFT가 아니다 | `ingest_lag_seq`·`ingest_state`부터. 피드가 정상이면 다음 회차가 본다 |
| `recon_inconclusive_total{reason="ENGINE_UNAVAILABLE"\|"ENGINE_CONTRACT"}` | 엔진에 닿지 못했거나 답이 계약 밖 — 재시도 0 | 엔진 상태·토큰 파일(§1)·계약 버전 확인. 다음 회차가 다시 본다 |
| `recon_inconclusive_total{reason="ESTIMATE_DIFF"}` | 열린 달(ESTIMATE)의 환수 상계·정정이 엔진 예상과 다르다 — DRIFT를 내지 않는다(설계서 §6.6 Q1 ⓑ′) | 확정 뒤 회차(CONFIRMED)가 다시 본다. 반복되면 엔진 예상의 기준 seq를 확인 |
| `inquiry_open_total`·`inquiry_open_oldest_age_seconds` | 답하지 않은 문의(대사 틱이 1분마다 갱신) | §7 `inquiry list --status=OPEN` → 답변 |

**테넌트 설정**(`tenant.params`, 없거나 형식이 다르면 앱 기본 `portal.recon.defaults.*`): `recon_hour_kst`(0~23, 기본 4), `auto_rebuild_enabled`(기본 true), `recon_caught_up_within_seconds`(기본 900), `recon_call_interval_ms`(기본 200), `recon_max_calls`(기본 500), `recon_max_seconds`(기본 900).

```sql
-- recon-params.sql — 예: 상한을 올리고 자동 재구축을 끈다
BEGIN;
SELECT set_config('app.tenant_id', '<TENANT_ID>', true);
UPDATE tenant SET params = params || '{"recon_max_calls": 2000, "auto_rebuild_enabled": false}'::jsonb WHERE tenant_id = '<TENANT_ID>';
COMMIT;
```

**연결·스레드**(계획 Q9 — P7-4·P7-5): 대사 회차는 회차 잠금을 쥔 바깥 트랜잭션의 연결 하나를 **회차 내내**(최대 `recon_max_seconds` + 재구축) 잡고, 저장·재구축은 새 트랜잭션으로 연결 하나를 더 쓴다 — 회차당 최대 2. 인제스트 틱은 적용 중 1(재구축 txB는 그 테넌트 잠금 안에서 1), 스케줄러 스레드는 둘(`spring.task.scheduling.pool.size: 2` — 인제스트 틱과 대사 틱이 서로를 기다리지 않는다). 그래서 HikariCP 최대 풀(기본 10)은 **대사 2 + 인제스트 1 + 동시 조회 요청 수** 이상이어야 한다 — 마감 익일 집중 접속(설계서 §10)과 대사 시각(`recon_hour_kst`)이 겹치지 않게 둔다. 인스턴스가 둘이면 회차 잠금이 테넌트당 하나만 돌게 한다(다른 인스턴스의 틱은 그 테넌트를 건너뛴다).

**재구축은 테넌트 하루(KST) 한 번**: 운영자가 낮에 `ingest rebuild`를 했어도 그날 자동 재구축 조건(오늘 재구축 0)은 대사 회차 기록(`recon_run.rebuilt_at`)만 본다 — 운영자 재구축은 회차 기록이 아니므로 그날 밤 자동 재구축을 막지 않는다.

**운영자 재구축과 DRIFT 표식**: `ingest rebuild`는 `earnings_month`를 이벤트로 다시 만들지만, 재생이 끝나는 트랜잭션(txB) 안에서 **재구축 끝 불변식**이 대사 표(`recon_result`)를 읽어 미해결 DRIFT가 있는 (설계사, 달)의 `data_status`를 `DRIFT`로 되살린다(설계서 §6.7 v1.11, 포털 Phase 8 ① — Phase 7 보고서 F11을 닫음). 운영자 재구축 뒤에도 그 달은 화면에 "확인 중"이다 — 따로 `recon run`을 부를 필요가 없다. "미해결"은 대사와 같은 규칙이다(그 DRIFT 행 이후 — 같은 시각 포함 — 같은 달의 `REPAIRED` 행이 없다). 재구축은 대사 표를 쓰지 않는다.
