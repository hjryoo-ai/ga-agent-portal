# 포털 운영 절차 (ga-agent-portal)

> 포털 Phase 3(조회 API·인증·인가)부터의 운영 등록 절차. 설계서 §9 v1.6이 정본이고 이 문서는 그 절차를 적는다. 값(발급자 URL·subject·설계사 ID·비밀)은
> 이 문서와 저장소 어디에도 쓰지 않는다 — 아래 SQL의 `<…>`는 자리표시다. 등록 SQL은 **파일**로 만들어 `psql -f`로 돌린다(셸 인자·환경 변수에 값을 싣지 않는다).
> 모든 등록·해제는 스키마 소유자 `portal_migrator`로, 그 테넌트를 세션에 설정한 트랜잭션 안에서 한다(`tenant`·`identity_link`는 FORCE RLS).

## 1. 테넌트 로그인 열기 — 발급자 등록

토큰의 `iss`가 테넌트를 정한다(설계서 §9). `oidc_issuer`는 정확 일치(대소문자·꼬리 슬래시 포함)이고 테넌트 사이에 유일하다. 둘 다 NULL이면 그 테넌트에는 로그인이 없다.

```sql
-- register-issuer.sql  (psql -v ON_ERROR_STOP=1 -f register-issuer.sql)
BEGIN;
SELECT set_config('app.tenant_id', '<TENANT_ID>', true);
UPDATE tenant SET oidc_issuer = '<https://idp.example/realms/ga01>', oidc_audience = '<portal-ga01>' WHERE tenant_id = '<TENANT_ID>';
COMMIT;
```

- 발급자 메타데이터(`<issuer>/.well-known/openid-configuration`)의 `issuer`가 이 값과 같아야 한다. JWKS는 그 메타데이터에서 받는다(등록된 발급자만 — 토큰이 고른 URL로는 나가지 않는다).
- 해제(로그인 닫기): 둘 다 NULL로. 다음 요청부터 401(캐시 없음).
- 발급자 표는 전용 롤 `portal_issuer`(이 세 열만)로 요청마다 읽는다 — 그 롤의 자격 증명은 `PORTAL_ISSUER_USER`·`PORTAL_ISSUER_PASSWORD`(비밀 관리자에서).

## 2. 설계사 링크 등록 — `identity_link` (AGENT)

설계사·역할은 이 행에서만 온다(토큰의 `agent_id`·`roles` 클레임은 쓰지 않는다). `org_path`는 포털 인가용 조직(v2 조직 조회의 범위) — 엔진의 `agent_profile.org_path`(표시용)와 출처가 다르고, 달라도 어느 쪽도 고치지 않는다.

```sql
-- link-agent.sql
BEGIN;
SELECT set_config('app.tenant_id', '<TENANT_ID>', true);
INSERT INTO identity_link (tenant_id, subject, agent_id, role, status, org_path, linked_at)
VALUES ('<TENANT_ID>', '<IdP subject>', '<AGENT_ID>', 'AGENT', 'ACTIVE', '</HQ1/BR03/TM07>', now());
COMMIT;
```

- 해제: `UPDATE identity_link SET status = 'REVOKED' WHERE tenant_id = '<TENANT_ID>' AND subject = '<IdP subject>';` — 행은 지우지 않는다(감사가 그 주체를 가리킨다). 다음 요청부터 404.
- `MANAGER`는 v2 조직 조회의 역할 — 지금 `/api/v1/me/**`는 `AGENT`만 열린다(`docs/authz-matrix.md`).

## 3. 운영자 등록 — CLI 인가 (OPERATOR)

운영 명령(`ingest status|resume|pause|rebuild`)의 행위자는 **실행한 OS 사용자**다 — subject `cli:<OS 사용자>`가 그 테넌트의 `OPERATOR`·`ACTIVE` 링크여야 한다(`--actor`는 없어졌다 — 쓰면 종료 코드 64). 운영자는 설계사가 아니므로 `agent_id`·`org_path`가 없다.

```sql
-- register-operator.sql
BEGIN;
SELECT set_config('app.tenant_id', '<TENANT_ID>', true);
INSERT INTO identity_link (tenant_id, subject, agent_id, role, status, org_path, linked_at)
VALUES ('<TENANT_ID>', 'cli:<os-user>', NULL, 'OPERATOR', 'ACTIVE', NULL, now());
COMMIT;
```

- 테넌트마다 따로 등록한다. 테넌트를 지정하지 않은 `ingest status`는 테넌트마다 확인해 등록되지 않은 테넌트를 `T not authorized`로 보이고, 하나라도 있으면 종료 코드 2.
- 거부는 그 테넌트의 `audit_access`에 `AUTHZ_DENIED`(detail `NO_LINK`·`REVOKED`·`ROLE`, target `cli:ingest <명령>`)로 남는다.
- `OPERATOR` 링크의 토큰으로 `/api`를 부르면 404다(설계사가 없다).
- 해제는 2와 같이 `REVOKED`.

## 4. `policyKey` 비밀 — 배포와 회전

응답의 `policyKey` = HMAC-SHA256(배포 비밀, `tenant_id` + `U+001F` + `policy_no`) 앞 16자(설계서 §7). 비밀은 파일 `portal.query.policy-key-secret-file`(환경 `PORTAL_POLICY_KEY_SECRET_FILE`, 기본 `/run/secrets/portal-policy-key`) — 32바이트 이상의 무작위 바이트, 소유자만 읽게. 웹 애플리케이션은 이 파일이 없으면 뜨지 않는다.

- **회전하면 모든 `policyKey`가 바뀐다.** 화면(Phase 4)은 키를 저장하지 않는다 — 북마크·저장된 필터의 키는 회전 뒤 빈 결과가 된다(오류가 아니다).
- 회전 절차: 새 비밀 파일 배치 → 인스턴스 순차 재시작(재시작 사이에는 인스턴스마다 키가 다를 수 있다 — 같은 화면이 두 인스턴스를 오가면 필터가 빈 결과일 수 있다).
- 비밀 값은 저장소·로그·티켓에 쓰지 않는다.

## 5. 동기화 지연 기준

`dataStatus = SYNC_DELAYED`의 기준 초는 테넌트 `params.sync_delay_seconds`(1~9자리 양의 정수), 없거나 형식이 틀리면 설정 `portal.query.default-sync-delay-seconds`(기본 300). 커서가 `RUNNING`이 아니면(재구축 중 포함) 기준과 무관하게 지연이다.

```sql
-- sync-delay.sql
BEGIN;
SELECT set_config('app.tenant_id', '<TENANT_ID>', true);
UPDATE tenant SET params = params || '{"sync_delay_seconds": 600}'::jsonb WHERE tenant_id = '<TENANT_ID>';
COMMIT;
```

## 6. 시뮬레이션 — 레이트 리밋·유지율 시나리오·로그 보존·엔진 타임아웃 (포털 Phase 5)

설계서 §9·§10 v1.8. 테넌트 값은 `tenant.params`, 엔진 타임아웃은 앱 설정이다(계획 Q10).

| 키 | 자리 | 기본 | 뜻 |
|---|---|---|---|
| `sim_rate_per_minute` | `tenant.params`(1~9자리 양의 정수) | 앱 설정 `portal.sim.default-rate-per-minute` = 10 | 설계사당 직전 60초 시뮬레이션 요청 수 상한 — 넘으면 429 `RATE_LIMITED` + `Retry-After` |
| `forecast_scenario_enabled` | `tenant.params`(JSON 불리언) | false | 분급 타임라인의 유지율 가정(RETENTION)을 연다 — 꺼져 있으면 `scenario=RETENTION`은 400, 화면에 토글이 없다 |
| `sim_log_retention_years` | `tenant.params`(양의 정수) | 3 | `simulation_log` 보존 연수 — **문서용**: 삭제 잡은 없다(지시문 ②). 아래 SQL을 운영자가 손으로 돌린다 |
| `portal.sim.connect-timeout` · `portal.sim.read-timeout` | 앱 설정(환경 `PORTAL_SIM_CONNECT_TIMEOUT` · `PORTAL_SIM_READ_TIMEOUT`) | 2s · 10s | 엔진 시뮬레이션 호출의 연결·읽기 시간 초과 — 넘으면 503 `ENGINE_UNAVAILABLE`, 재시도 없음 |

```sql
-- sim-params.sql — 리밋 20/분, 유지율 시나리오 켬
BEGIN;
SELECT set_config('app.tenant_id', '<TENANT_ID>', true);
UPDATE tenant SET params = params || '{"sim_rate_per_minute": 20, "forecast_scenario_enabled": true}'::jsonb WHERE tenant_id = '<TENANT_ID>';
COMMIT;
```

보존 정리(테넌트마다, 손으로 — 같은 조건의 `SELECT count(*)`를 먼저 보고 지운다). 재구축은 `simulation_log`를 지우지 않는다(설계서 §6.7):

```sql
-- sim-log-retention.sql
BEGIN;
SELECT set_config('app.tenant_id', '<TENANT_ID>', true);
DELETE FROM simulation_log
 WHERE tenant_id = '<TENANT_ID>'
   AND created_at < now() - make_interval(years => coalesce((SELECT (params->>'sim_log_retention_years')::int FROM tenant WHERE tenant_id = '<TENANT_ID>'), 3));
COMMIT;
```

엔진 서비스 토큰은 인제스트와 같은 파일(`PORTAL_ENGINE_TOKEN_DIR/<TENANT_ID>`)이다 — 파일이 없으면 시뮬레이션은 엔진을 부르지 않고 503(로그 사유 `TOKEN_MISSING`)이고 조회는 그대로다.
